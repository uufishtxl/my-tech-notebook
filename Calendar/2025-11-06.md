## 关于 Access Token 和 Refresh Token

以使用 SimpleJWT 为例：

* 网页中：Login提供账号密码获取 Access Token。当重新访问Token保护的 API 时，一旦发现Token过期了，就会自动通过拦截器，使用登录时获取的 Refresh Token (通常存在 `httpOnly` Cookie 中)，去请求 `/api/token/refresh/` 接口，从而置换到新的 Access Token。
* POSTMAN：POSTMAN没有这个功能。因此有一个 WORKAROUND是：
  * 创建环境和环境变量。并且在POSTMAN中激活这个环境。
  * 在CALL LOGIN API 时，将 RESPONSE DATA 中 ACCESS 的值保存到环境变量中。
  * 新建一个 REFRESH POST REQUEST，呼叫“api/token/refresh”，即可“手动”完成用旧TOKEN置换新TOKEN这个动作（它依赖的是 Postman 自动发送的 `refresh` Cookie 来进行身份验证，不依赖 Access Token 或 Body。因此不需要配置 AUTH，也不需要在 BODY中提供任何数据，但是需要在后端配置这个路由，比如：path('api/token/refresh/', get_refresh_view().as_view(), name='token_refresh')）
 * 其他需要TOKEN保护的 API 请求，都在 Authrization 中选择 Bearer Token，然后值用环境变量的值即可。每次发现过期，手动呼叫下 REFRESH API 即可。

## 偷懒的方法：改配置

在 `settings.py` 中：

```python
# simple-jwt 的专门设置
if DEBUG:
```

# Django 项目处理 Export 请求
## 简单场景

*  前端实现：非常简单，一个 `<a>` 标签就能搞定。`<a href="/api/v1/phrases/export/?format=csv" download>导出 CSV</a>` 或者直接在 `JavaScript 中 window.location.href = '...'`。
* 后端实现：从 URL query parameters (request.GET)中获取参数，然后返回一个带有特殊 Content-Disposition头的 HTTP Response，浏览器会自动触发下载。

  * 优点：简单、快速，符合 RESTful 风格（获取资源）。
  * 缺点：如果筛选条件复杂，URL 可能会过长；筛选参数会暴露在 URL 中。

## 复杂场景：使用 POST 请求 (更推荐)

  如果你的导出需要复杂的筛选条件（比如多个字段、日期范围、复杂的搜索关键字等），那
  么用 POST 是更稳健、更灵活的选择。

   * 前端实现：
       1. 使用 fetch 或 axios 发送一个 POST 请求。
       2. 将所有筛选条件放在请求的 body 中（通常是 JSON 格式）。
       3. 接收到后端返回的文件流（Blob），在前端手动创建一个下载链接来触发下载。
   * 后端实现：
       1. 从请求的 body (request.data) 中获取筛选条件。
       2. 根据条件查询数据。
       3. 同样，返回带有 Content-Disposition 头的文件流。

### 优点:
   * 没有长度限制：可以在请求体中传递非常复杂的 JSON 对象作为筛选条件。
   * 更安全：筛选条件不会保留在浏览器历史或服务器日志的 URL 中。
   * 更强大：可以传递更丰富的数据结构。

### 缺点
 前端实现比 GET 稍微复杂一点。

### 总结与建议

对于一个功能完备的应用，强烈建议你使用 POST
请求。这样可以一步到位，支持未来可能增加的各种复杂筛选需求。

这个过程分三步：

### Views
几个知识点：
- `@api_view(['POST'])`装饰器，作用是给一个普通的 Python 函数赋予强大的 API 功能：
   * 转换视图：将一个普通的函数 `export_phrase_view`转换成一个 DRF 能识别的 API 视图。
   * 限定方法：`['POST']`参数告诉这个视图只接受 POST 请求，如果用 GET 或其他方法访问，会直接返回错误。
* 为什么这里可以直接读取 Request 数据，而不需要从 JSON 转换为 Python 数据：这是 DRF 的特性，能自动解析传入的 JSON 数据，并放到 `request.data` 中，方便使用。
* View 的编写可以有两种方法：
	- `Class`：之前都是用 `Class`的方法，就需要集成 APIView 或者 ListAPIView 之类的。
	- `method`：这里用了 `method`方法，就需要用到这两个装饰器。
	这里还要总结下类视图和函数视图各自的优缺点、以及适用的场景。比如为什么这里 Export 就用了FBV，而不是类视图。
- 不想要导出某个字段应该怎么做：在 `data = list(queryset.values(...))`中移除该字段即可
- `df.rename(...)`中的 `inplace` 表示
- `buffer=io.BytesIO()` 创建一个“内容存中二进制文件对象”。具有速度快、安全和简洁的特性。`buffer=seek(0)` 的作用是将内存对象的读写指针移动到文件开头（位置为0）。其占用的空间在 HttpResponse 发送完成后会被回收。

```python
@api_view(['POST'])
@permission_classes([IsAuthenticated])
def export_phrases_view(request):
    """
    导出用户短语数据为 Excel 文件。
    接收一个包含要导出的 phrase logs 的 ID 列表的 POST 请求。
    如果未提供 ID，则导出该用户的所有短语。
    """
    user = request.user
    log_ids = request.data.get('ids', None)
    if log_ids:
        queryset = PhraseLog.objects.filter(user=user, pk__in=log_ids)
    else:
        queryset = PhraseLog.objects.filter(user=user)
    # 定义要导出的字段
    data = list(queryset.values(
        'expression_text',
        'chinese_meaning',
        'example_sentence',
        'original_context',
        'created_at',
        'remark'
    ))
    if not data:
        return Response({"error": "没有可导出的数据"}, status=status.HTTP_404_NOT_FOUND)
    # 创建 Pandas DataFrame
    df = pd.DataFrame(data)
    # 【修复】将 'created_at' 列转换为无时区，以兼容 Excel
    if 'created_at' in df.columns:
        df['created_at'] = pd.to_datetime(df['created_at']).dt.tz_localize(None)
    # 重命名字段以获得更友好的列标题
    df.rename(columns={
        'expression_text': '短语',
        'chinese_meaning': '中文含义',
        'example_sentence': '例句',
        'original_context': '原始上下文',
        'created_at': '创建时间',
        'remark': '备注'
    }, inplace=True)
    # 将 DataFrame 写入内存中的 Excel 文件
    buffer = io.BytesIO()
    with pd.ExcelWriter(buffer, engine='openpyxl') as writer:
        df.to_excel(writer, index=False, sheet_name='Phrases')
    buffer.seek(0)
    # 创建 HTTP 响应
    response = HttpResponse(
        buffer,
        content_type='application/vnd.openxmlformats-officedocument.spreadsheetml.sheet'
    )
    response['Content-Disposition'] = 'attachment; filename="phrases_export.xlsx"'
    return response
```

# 模型业务逻辑：重写 save 函数

有这样一个任务：实现 `failed_ratio` 的同步逻辑（例如，在 `PhraseLog.save()` 方法中自动计算）。
这是一个基于 Model 数据的业务逻辑。因此可以直接在模型本身上实行这个逻辑。这样做的好处是，无论是通过 API、Django 后台还是其他任何形式修改了数据，这个计算逻辑都会被自动触发，从而保证了数据的一致性。

```Python
class PhraseLog(models.Model):
	# ...
    def save(self, *args, **kwargs):
        if self.tested > 0:
            ratio = (self.failed / self.tested) * 100
            self.failed_radio = int(round(ratio))
        else:
            self.failed_radio = 100
        super().save(*args, **kwargs) # Call the "real" save() method.
```
