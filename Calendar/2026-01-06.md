
## DITA Reference

**核心结构**

* `<refbody>`：主体
* `<table>`：通用表格
* `<properties>`：专门用于“两列式” (Key-Value Pair)，比 Table 简单

### CALS Table

比 HTML 表格（`<table>`/`<tr>`/`<td>`）要繁琐，支持极其复杂的排版（合并单元格、列宽定死、表头跨页重复等）。

```XML
<table>
  <tgroup cols="2"> <colspec colname="c1" colwidth="1*"/> <colspec colname="c2" colwidth="1*"/>
    <thead> <row>
        <entry>Parameter</entry>
        <entry>Value</entry>
      </row>
    </thead>
    <tbody> <row>
        <entry>Voltage</entry>
        <entry>220V</entry>
      </row>
    </tbody>
  </tgroup>
</table>
```

手动编写 CALS Table 非常痛苦，完全可以通过 Python 脚本生成 DITA XML。

#### `colspec`

* `colwith`，如果是数字+`*`格式，比如 `1*`，类似 CSS Flexbox 中的 `1fr`。如果直接输入数字，建议带上单位，比如 `8cm`、`120pt`或`3in`；
* `colsep`和`rowsep`：这是控制内部边框线的。用 `0` 和 `1` 控制。
	* `0` 表示没有线
	* `1` 表示右边/下边画一条竖/横线
	
	外边框由`<table>`标签上的 `frame` 属性控制（比如 `frame="all"`）表示四边都有线。
* 表头跨页重复：DITA 天然天性。

### `<properties>`标签

如果只是想列出简单的“参数-值”，不要用重型武器 CALS Table。DITA 有轻量级的 `<properties>`。
* **场景**：错误码列表、环境配置表、硬件规格
* **优势**：结构极其简单，不用管列宽，自动对齐

```XML
<properties>
    <property>
        <proptype>Voltage</proptype>
        <propvalue>220V</propvalue>
    </property>
    <property>
        <proptype>Frequency</proptype>
        <propvalue>50Hz</propvalue>
    </property>
</properties>
```

### `<refsyn>` - Reference Syntax

* **场景**：用来描述命令行语法、API 签名、函数参数
* **位置**：通常在 `refbody` 的最前面
* **例子**：
```XML
<refsyn>
	<cmdname>django-admin</cmdname>
	<kwd>startproject</kwd>
	<var>projectname</var>
</refsyn>
```

### 📝 核心总结：理解 DITA 的 refsyn

**1. refsyn 的两种核心使用场景**  
`refsyn` 是 `<reference>` 主题的“摘要”或“用途声明”区，主要服务于机器检索和内容管理。其具体形态由主题类型决定：

|场景类型|描述性 refsyn|语法性 refsyn|
|---|---|---|
|**描述对象**|**概念、对象、字段**的用途|**命令、函数、语句**的语法|
|**内容形式**|一段**自然语言摘要**，解释“是什么”和“为什么”。|一个**结构化语法块**，使用 `<kwd>` (关键词)、`<var>` (变量)、`<sep>` (分隔符) 等标签精确展示“怎么用”。|
|**主要目的**|让机器提取关键术语，理解主题上下文，便于内容关联和检索。|让机器精确解析语法结构，支持智能发布（如语法高亮、参数提示）和自动化处理。|
|**典型用例**|软件API参考、配置参数说明。|CLI命令手册、编程语言语法参考。|

**2. 为什么连空格都必须用 `<sep>` 标签？**  
这体现了DITA“内容与表现分离”的核心哲学。一个空格在视觉上是“格式”，但对于机器而言是歧义的：它可能是语法的一部分，也可能是无关紧要的排版空格。用 `<sep>` 包裹空格，是**赋予其明确的“语法分隔符”语义**。

**这样做是为了：**

- **无歧义的机器理解**：确保在任何处理流程（如转换、翻译）中，分隔符都不会被丢失或误解。
    
- **样式与控制的完全解耦**：发布时，可通过样式表将 `<sep>` 的内容（一个空格）轻松替换为换行、竖线等任何形式，而**无需改动源文件**。
    
- **支持复杂自动化**：为未来的语法验证、智能补全等高级功能提供结构化基础。
    

**3. refsyn 与 codeblock 如何互补**  
在技术文档中，`refsyn` 和 `<codeblock>` 分工明确，形成完美互补：

|元素|refsyn (通常与 `<synph>` 配合)|codeblock|
|---|---|---|
|**核心目的**|**定义“语法”**。为机器提供精确的、结构化的**语法模型**。|**展示“代码”**。为人类提供可阅读、可复制的**完整示例或算法片段**。|
|**内容性质**|是**元数据**和**蓝图**。内容被拆解为带有语义的零件（`<kwd>`, `<var>`）。|是**成品**和**实景**。内容通常是完整的、自由格式的文本块。|
|**主要使用者**|**机器**（用于处理）与**需要快速把握结构的人**。|**阅读和学习的人**。|
|**典型位置**|位于主题开头，作为官方、权威的语法声明。|位于示例、教程或说明段落中，用于阐释用法。|

**一句话概括二者关系：`refsyn` (`<synph>`) 是给机器和开发者看的“语法图纸”，而 `<codeblock>` 是给读者看的“实物照片”。**

### 💡 给你的最终建议

- **接受设计哲学**：理解DITA是为“**内容管理和自动化**”而设计，而非为“**写作便利**”而优化。它是一种面向规模化、长期化和智能化的解决方案。
    
- **应用二八法则**：对文档中最核心、最常用、变更最频繁的**20%的关键语法**进行结构化标记（使用`<synph>`），这能带来80%的维护和自动化收益。对于复杂但次要的代码，直接用`<codeblock>`更高效。
    
- **评估使用场景**：如果你的文档体系庞大、需要多语言支持、严格版本管理或准备接入AI，那么DITA的严谨性（包括`<sep>`这类标签）是值得投入的。否则，轻量级标记语言（如Markdown）可能是更合适的选择。

### ✅ Day 3 复盘：Reference 与数据管理

**1. 核心定位 (Definition)**

- `Reference` = **数据库 (Database)**。
    
- 它只存事实（参数、规格、错误码、配置项），不包含步骤。
    

**2. 三种数据的最佳载体 (The "Right" Tool)**

- **复杂数据 (Excel)** $\rightarrow$ 用 **`<table>` (CALS)**。
    
    - _全栈策略_：别手写，用 Python 脚本把 JSON/Excel 自动转成 XML。
        
- **键值对 (KV Pair)** $\rightarrow$ 用 **`<properties>`**。
    
    - _策略_：比 Table 轻量，适合写环境配置。
        
- **代码/命令 (Code)** $\rightarrow$ **首选 `<codeblock>`**。
    
    - _避坑_：除非面试官逼你，否则别碰 `<refsyn>`。它就是过度设计的产物。
        

**3. “仓库”策略 (The Warehouse Strategy)**

- **概念**：建立一个不发布的 `warehouse.dita` (Reference 类型)。
    
- **写法**：用 `<ph id="var_name">Value</ph>` 存变量。
    
- **用法**：用 `conref` 在其他几百个文件里引用它。
    
- **价值**：实现 **Single Source of Truth**（一处修改，全局更新）。
