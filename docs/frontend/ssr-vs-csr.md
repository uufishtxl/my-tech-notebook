# 核心面试题：SSR vs CSR (前端渲染模式深度对比)

## 1. 核心概念

* **SSR (Server-Side Rendering) - 服务器端渲染**
    * **代表技术：** Django Templates, PHP, JSP, Ruby on Rails, (以及现代的 Nuxt.js / Next.js)。
    * **工作模式：** 服务器（Server）接收到请求后，在**服务器端**将数据和模板组合生成**完整的HTML**，然后将这个HTML字符串发送给浏览器。浏览器“开箱即用”。

* **CSR (Client-Side Rendering) - 客户端渲染**
    * **代表技术：** Vue.js, React, Angular。
    * **工作模式：** 服务器只发送一个几乎**空白的HTML**（俗称“应用外壳”，App Shell）和大量的JavaScript（框架本身）。浏览器接收到后，**在浏览器里**执行JS，动态地抓取API数据，并**在客户端**渲染出页面内容（DOM）。

## 2. 深度对比表 (面试关键点)

| 对比维度 | SSR (服务器端渲染) | CSR (客户端渲染) |
| :--- | :--- | :--- |
| **工作地点** | 服务器 | 浏览器 (客户端) |
| **首次加载速度 (FCP)** | ⚡️ **快** | 🐢 **慢** |
| (First Contentful Paint) | 浏览器直接渲染收到的HTML。 | 需下载JS -> 执行JS -> 请求API -> 渲染DOM。 |
| **后续交互体验** | 🐢 **慢** | ⚡️ **快** |
| (Navigation) | 每次导航/点击都需**刷新页面**，向服务器重新请求。 | 无需刷新页面，路由和视图切换在客户端完成，体验流畅。 |
| **SEO 友好度** | ✅ **极好** | ⚠️ **差 / 需额外处理** |
| (搜索引擎优化) | 爬虫直接抓取到完整内容的HTML。 | 爬虫抓到的是“空壳HTML”，不一定能正确执行JS并等待API。 |
| **服务器压力** | 💨 **大** | 💧 **小** |
| | 每次请求都要在服务器上“实时渲染”HTML。 | 服务器只作为API（JSON）或静态文件（JS/CSS）提供者。 |
| **客户端压力** | 💧 **小** | 💨 **大** |
| | 浏览器只负责渲染简单的HTML。 | 浏览器需要执行复杂的JS逻辑和DOM操作。 |
| **最佳应用场景** | 内容驱动型网站（博客、新闻、电商门户）、企业官网。 | 高交互型应用（管理后台、SaaS、复杂表单、SPA）。 |

## 3. 选型与权衡 (面试必问)

**面试官：“在项目中，你如何选择SSR还是CSR？”**

> “这取决于项目的核心需求。
>
> 1.  如果我构建的是一个**内容驱动、对SEO排名要求极高**的网站，比如博客或电商网站，我会优先选择**SSR**。因为它能保证最快的首屏内容展现（FCP）和完美的SEO。
> 2.  如果我构建的是一个**功能驱动、高交互性**的应用，比如一个内部管理后台或SaaS工具，我会选择**CSR**（比如我的Vue/React技术栈）。因为在这种场景下，SEO并不重要，而用户操作的**流畅性、无刷新体验**是第一位的。”

## 4. 延伸考点 (加分项)

* **SSG (Static Site Generation) - 静态网站生成**
    * **代表：** Jekyll (你提到的！), Hugo, Hexo。
    * **模式：** 在**构建时(Build Time)**就提前生成所有页面的**纯静态HTML文件**。
    * **优点：** 兼具SSR的SEO友好和CSR的（服务器）低压力，速度极快（因为是纯静态文件）。
    * **缺点：** 内容更新后需要**重新构建**整个网站。

* **“同构”与“元框架” (CSR的SEO解决方案)**
    * **Nuxt.js (Vue) / Next.js (React):** 这些框架（称为“元框架”）实现了“同构”。它们可以在服务器端**首次渲染**（实现SSR的优点），然后在客户端“接管”(Hydration)，**激活**成一个CSR应用（实现CSR的优点）。这是目前业界的“最优解”之一。
