# N+1 查询问题详解

## 什么是 N+1 问题？

假设你有两个表：**作者 (Author)** 和 **书籍 (Book)**，一个作者有多本书。

### 错误写法（产生 N+1）
```python
# FastAPI + SQLAlchemy 示例
authors = db.query(Author).all()  # 第 1 次查询：获取所有作者

for author in authors:
    print(author.books)  # 每个作者触发 1 次查询！
```

**执行的 SQL**：
```sql
SELECT * FROM authors;           -- 1 次
SELECT * FROM books WHERE author_id = 1;  -- +1
SELECT * FROM books WHERE author_id = 2;  -- +1
SELECT * FROM books WHERE author_id = 3;  -- +1
...
-- 如果有 100 个作者，就是 101 次查询！
```

这就是 **N+1 问题**：1 次查主表 + N 次查关联表。

---

## 为什么这是个问题？

| 查询次数 | 网络开销 | 数据库压力 |
|---------|---------|-----------|
| 101 次 | 极高 | 极高 |
| 1-2 次 | 低 | 低 |

在生产环境中，这会导致**接口变慢、数据库被打爆**。

---

## 如何解决？

### SQLAlchemy（FastAPI 常用）

```python
from sqlalchemy.orm import joinedload, selectinload

# 方法 1：joinedload（用 JOIN 一次查完）
authors = db.query(Author).options(joinedload(Author.books)).all()
# SQL: SELECT * FROM authors LEFT JOIN books ON ...

# 方法 2：selectinload（两次查询，Python 合并）
authors = db.query(Author).options(selectinload(Author.books)).all()
# SQL: SELECT * FROM authors; SELECT * FROM books WHERE author_id IN (1,2,3...);
```

### 什么时候用哪个？

| 方法 | SQL 方式 | 适用场景 |
|------|---------|---------|
| `joinedload` | 一次 JOIN | 一对一、多对一 |
| `selectinload` | 两次查询 + IN | 一对多、多对多 |

---

## Django 对照（可选）

| SQLAlchemy     | Django ORM         |
| -------------- | ------------------ |
| `joinedload`   | `select_related`   |
| `selectinload` | `prefetch_related` |

---

## 一句话总结

> **N+1 = 忘记预加载关联数据，导致循环里每次都查数据库。**
> **解决 = 用 `joinedload` 或 `selectinload` 预加载。**

## 实操

### N+1 查询

```python
from django.db import connection, reset_queries
from sandbox.models import Book, Author

# 假设 Author 有 5 条记录； Book 有 15 条记录

reset_queries()

books = Book.objects.all()

for book in books:
	print(book.author.name)
	
print(f"总共执行了: {len(connection.queries)} 条 SQL") # 发现查询了 16 次。
```

### `select_related`

在 FASTAPI 中对应 `joinedload`。

```python
from django.db import connection, reset_queries
from sandbox.models import Book, Author

reset_queries()

books = Book.objects.select_related('author').all()

for book in books:
	print(book.author.name)

print(f"总共执行了: {len(connection.queries)} 条 SQL") # SQL 只执行了 1 次
```

### `prefetch_related`

对应 FASTAPI 中的 `selectinload`。

查询某个作者所有的书，虽然直觉上，我们可能希望 author 对应一个 book 列表，但是在 SQL 层面是无法实现的。

```python
from django.db import connection, reset_queries
from sandbox.models import Author, Book

reset_queries()

authors = Author.objects.prefetch_related('books').all() # 默认是 book_set，但是因为我们在对 Book Model 中的 Author field 定义时，用了 related_name='books'，全行：author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name='books')

for author in authors:
	print(author.books.all())

print(f"总共执行了: {len(connection.queries)} 条 SQL") # SQL 执行了 2 次
# 1. SELECT * FROM author
# 2. SELECT * FROM book where author_id IN (...)
```

## `SELECTIN`底层 SQL 执行流和内存映射机制

### 第一步：主表查询

```SQL
SELECT id, content FROM script;
```

### 第二步：利用 `IN` 语句进行关联查询

```SQL
-- ORM 自动拼接出包含所有主键的 IN 条件，一次性把关联标签全捞出来
SELECT tag.id, tag.name, script_tags.script_id FROM tag
INNER JOIN script_tags ON tag.id = script_tags.tag_id
WHERE script_tags.script_id IN (1, 2, 3, ..., 1000);
```

对上面SQL语法的解释：

#### 第一步：建立基准表（左表）
```SQL
FROM tag
```
数据库引擎收到指令，先把 `tag` 表整个读到内存里，作为拼接的底座。

#### 第二步：拉取目标表并声明拼接规则（右表）
数据库把中间隐藏的中间表 `script_tags` 也拉到内存里准备着：
```SQL
INNER JOIN script_tags
```

- `INNER` 表示”严格交集“。如果 `tag` 表里的某个标签（比如“未分类”），在 `script_tags` 里根本找不到对应记录，那就直接把这个标签扔掉，绝对不出现在最终结果里。

`script_tags`大概长这样：

| id  | script_id | tag_id |
| --- | --------- | ------ |
| 100 | 50        | 1      |
| 101 | 88        | 1      |
| 102 | 50        | 2      |
**Django 在底层到底瞒着你干了什么？**

当你在 Django 的 `Script` 模型里写下 `tags = models.ManyToManyField(Tag)` 这短短一行代码时：

1. **隐式建表**：Django 在执行 `python manage.py migrate` 的时候，发现这是一个多对多字段，它会自动在底层数据库里执行一条 `CREATE TABLE` 的 SQL 语句，凭空建出这张名叫 `appname_script_tags` 的第三张表（也就是上面的这张表）。
    
2. **强制去重（联合唯一索引）**：为了防止数据脏污，Django 会在底层的数据库表上，给 `(script_id, tag_id)` 这两列强行加上一个 `UNIQUE` 联合约束。物理上保证了：台词 50 绝对不可能被重复打上两次标签 1。
    
3. **封装查询**：当你用 `script.tags.all()` 时，Django 会自动生成我们上一回合说的那种 `INNER JOIN` 语句，顺着这张中间表摸过去，把对应的 Tag 名字拿回来。


#### 第三步：自动齿轮咬合（匹配引擎）
```SQL
ON tag.id = script_tags.tag_id
```
数据库引擎开始进行逐行扫描：拿起 `tag`表的第一行（假设 `id=1`, `name="Sarcasm`），转头去 `script_tags` 表里疯狂搜索”谁的 `tag_id` 是 1？“只要找到了，数据库就会在内存里把这两行数据的列，水平横向粘合在一起。


### 一对一、一对多、多对一、多对多

判断两张表到底是什么关系，你只需要在脑子里进行一次**“双向灵魂拷问”**：
1. **正向问**：一个 A，能拥有多个 B 吗？
2. **反向问**：一个 B，能属于多个 A 吗？
---

### 1. 一对一 (One-to-One) = 强行拆分的“加长版”数据

- **拷问结果**：正向 (No) + 反向 (No)
- **物理本质**：这两张表的数据，其实**完全可以合并成一张表**。之所以拆开，通常是因为主表太宽了，或者有些数据不常用。
- **真实场景**：系统的 `User`（用户表）和 `UserProfile`（用户偏好设置表）。
    - 一个用户，只能有一套偏好设置 (No)。
    - 一套具体的偏好设置，只能属于这一个用户 (No)。
- **Django 实现**：`OneToOneField`。不管放在哪边，底层都是一个带有 `UNIQUE` 约束的外键。
    

### 2. 一对多 / 多对一 (1:N / N:1) = 绝对的“归属权”
- **拷问结果**：正向 (Yes) + 反向 (No) 或 正向 (No) + 反向 (Yes)
- **物理本质**：这就是同一个物理结构，**完全取决于你站在哪边说话**。
- **真实场景**：《老友记》的剧集 (`Episode`) 和 季 (`Season`)。
    - **你站在 Season 的角度往下看（一对多）**：第 1 季里面，包含了 24 集 (Yes)。
    - **你站在 Episode 的角度往上看（多对一）**：第 1 季第 1 集，只能属于第 1 季，绝对不可能同时属于第 2 季 (No)。
- **物理建表铁律**：永远只在“多”的那一边，建一个外键。
- **Django 实现**：在 `Episode` 模型里写 `ForeignKey(Season)`。

### 3. 多对多 (Many-to-Many) = 复杂的交集
- **拷问结果**：正向 (Yes) + 反向 (Yes)
- **物理本质**：当两边都能拥有对方的多个实例时，关系就彻底乱了。数据库在物理层面**根本无法直接把两张表连起来**，必须找一个“第三者”来牵线搭桥，也就是必须建一张**隐藏的中间表（Junction Table）**。
- **真实场景**：Lingua Workbench 里的台词 (`Script`) 和 标签 (`Tag`)。
    - **正向看**：Chandler 的一句台词 "Could I _be_ wearing any more clothes?"，可以同时打上 "Sarcasm" (讽刺) 和 "Joey" 两个标签 (Yes)。
    - **反向看**："Sarcasm" 这个标签，也可以同时挂在几百句不同的台词下 (Yes)。
- **Django 实现**：在其中一边写 `ManyToManyField`。Django 会在底层悄悄帮你建一张 `script_tags` 中间表，里面只有两列：`script_id` 和 `tag_id`。
