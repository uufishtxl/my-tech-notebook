## 1. 核心复习 (Review Items)

### Q1. [DRF/ViewSet] get_object() 内幕
当我们在 `ViewSet` 的 `update()` 或 `retrieve()` 方法中显式调用 `self.get_object()` 时，该方法的内部执行顺序是什么？（涉及数据库获取、404 处理、权限校验）。这个顺序的设计动机（DRF 核心防御价值）是什么？

**答案**: 先回执行 `get_object_or_404`获取数据。如果没有获取到数据，则用 404 处理报错。如果货到数据再执行 `check_object_permissions`，如果用户没有相关权限，报403，如果是未授权用户，报 401。这样的顺序是为了防止黑客探取账号是否有权限访问数据。

> 💡 **解析**：
> 1. **执行顺序**：`get_queryset()` -> `filter_queryset()` -> `get_object_or_404()` -> `check_object_permissions()`。
> 2. **防御价值**：先执行 `filter_queryset`（如配合 `IsOwner` 过滤）可以确保用户根本查不到不属于自己的数据（返回 404），而 `check_object_permissions` 则是最后一道生命线，用于更细粒度的逻辑校验。这种设计避免了在没获取到对象前就进行权限判定，同时也隐藏了资源的存在性（避免通过 403 探测资源 ID 是否存在）。


### Q2. [DRF/Serializer] Read-only 字段的显式与隐式声明考量
在 DRF 中，某些字段由于 Model 的定义（如 `auto_now_add=True`）会自动被识别为 `read_only`。既然它们已经是隐式只读的，为什么在工业级开发中我们依然提倡在 Serializer 的 `Meta.read_only_fields` 中再显式写一遍？

**答案**: 一方面是为了能够防止后续其他人维护时，由于中间出了一些意外而导致问题（特别是对一些原来定义为 `ReadOnlyModelViewSet` 的情况。另外一方面，显示再写一遍，更有利于可读性和维护性。

> 💡 **解析**：
> 1. **契约化 (Explicit Contract)**：`read_only_fields` 是对前端的公开契约，显式声明能让协作开发者一眼看出哪些字段不可写。
> 2. **防御性编程**：防止 Model 层面的定义变更（如删掉 `auto_now_add`）导致 API 意外变得可写。
> 3. **Swagger/OpenAPI 支持**：有助于自动化文档生成工具正确标记 `readOnly` 属性。


### Q3. [API Architecture] 嵌套路由归属权 (Action vs Filter)
假设我们要实现一个“查询某个戏剧 (Drama) 下的所有季度 (Season)”的接口。方案 A 是在 `DramaViewSet` 中添加 `@action(detail=True)`；方案 B 是创建一个 `SeasonViewSet` 并通过 `GET /seasons/?drama_id=1` 过滤。请分析这两者的优劣，并说明为什么 **API First** 架构通常更提向后者。

**答案**: 方案 A 的路由会是 `/api/v1/dramas/1/seasons`，这非常符合 Restful API 的设计原则。但是，会需要在 `DramaViewSet` 中添加 `Season` Model的数据获取逻辑 and Serializer 序列化。方案 B 在路由上没有方案 A 好，但是在 `ViewSet` 的逻辑中不会出现方案 A 的藕合的情形，因此更符合 API First 架构。

> 💡 **解析**：
> 方案 B (Filter) 优于方案 A (Action)。
> 1. **解耦**：`DramaViewSet` 不应关心 `Season` 的序列化细节。
> 2. **契约优先 (API First)**：方案 B 保持了资源的正交性，方便后续扩展 `Season` 的搜索、排序和分页。
> 3. **灵活性**：过滤接口可以轻松支持多维度查询（如按年份、按名称），而 Action 通常功能单一。


### Q4. [Django/DRF] read_only_fields 的防御边界
`read_only_fields` 配置只能拦截 API 层面的修改吗？如果我在后端业务逻辑中（非 API 调用）通过 `MyModel.objects.create(...)` 或 `instance.field = X; instance.save()` 直接操作数据，这个配置还有效吗？

**答案**: Yes, it can only forbids updates from an API request. This configuration does not work for pure-end logic handling mentioned.

> 💡 **解析**：
> **✅ 答对啦！**
> **专业表达**：Correct. `read_only_fields` acts as a guard at the **serializer level**. It does not prevent modifications via lower-level **ORM operations** (e.g., `.create()`, `.update()`, or `.save()`) within your server-side logic.

### Q6. [Django/Models] JSONField default=dict 防御艺术
在定义 Django 的 `JSONField` 时，为什么官方和社区更推荐使用 `default=dict` 而不是 `null=True`？在进行 `.filter()` 查询时，如果不设置合理的默认值会遇到什么麻烦？

**答案**: Because if a field accepts nullable values, that mean in both frontend and backend logic, developers have to frequently make double-data-type-check to avoid errors. And using `defualt=dict` totally can avoid such troubles. I do not know what do you mean by saying 'reasonable default'.

> 💡 **解析**：
> **✅ 思路正确！** "Reasonable default" 即指 `default=dict`。
> 1. **回避 Null 陷阱**：`null=True` 会导致在 `.filter(data__key='value')` 时跳过那些值为 `NULL` 的行，而 `default=dict` 确保所有行都是有效的容器。
> **专业表达**：Using `default=dict` ensures a **consistent data type** (it's always a dictionary), eliminating tedious null checks (e.g., `if instance.field is not None`) in both frontend and backend code.


### Q7. [Requests] raise_for_status
在 Python 的 `requests` 库中，`response.raise_for_status()` 的具体作用是什么？在编写健壮的爬虫或 API 客户端时，为什么建议在拿到响应后紧跟这一行？

**答案**: Assume that we've  made a request to a third-party API, and it returned an error response. if `response.raise_for_status` is absent, then the error itself will be wrapped as a 'normal' reponse and be sent back to the client side. This is not acceptable.

> 💡 **解析**：
> **✅ 理解正确！**
> 默认情况下，`requests` 即使收到 4xx/5xx 也不会抛出异常。`raise_for_status()` 实现了 **快速失败 (Fail Fast)** 原则。
> **专业表达**: "It triggers an `HTTPError` for 4xx/5xx status codes. This ensures that the application **fails fast** instead of proceeding with an invalid or error-laden response body."


### Q8. [Django/Auth] AUTHENTICATION_BACKENDS
在 Django 的配置文件中，`AUTHENTICATION_BACKENDS` 的作用是什么？如果你集成了 `django-allauth` 或其他第三方登录插件，为什么要修改这个配置，而不是只写 `INSTALLED_APPS`？

**答案**: Because django defaults to implment authentication based on the 'user' field. That is to say, email will not be involved in authentication. So when we have to check user permissions by reading the email, this step is required.

> 💡 **解析**：
> **✅ 基本正确。**
> 核心在于 Django 的 `authenticate()` 会轮询 this list。
> **专业表达**: "It defines a list of classes used to authenticate users. Overriding it is necessary when using packages like `django-allauth` to support **alternative authentication flows** (like Email, OAuth, or LDAP) that are not part of the default username-based system."


### Q9. [CSS] Stacking Context (层叠上下文)
除了 `z-index` 本身的值太小，还有哪些常见的 CSS 属性（写在父元素上）会导致子元素的 `z-index` 失效，无法盖过外部的元素？为什么 `Teleport` 组件能从根本上解决这个问题？

**答案**: An elment wrapped in `<Transition>`, or posessing `object-filter` or `opacity` CSS properties will be stacked under an element. This means all its children elements cannot override the z-indexing of that parent element. By teleporting an element, it will be bound with the `<body>` element, so problem solved.

> 💡 **解析**：
> **✅ 答对啦！**
> **专业表达**: "Properties like `opacity` (< 1), `transform` (not none), or `filter` (not none) create a new **stacking context**. This creates a 'z-index trap' where children cannot escape their parent's stack. `Teleport` solves this by mounting the element to the `<body>` level, bypassing the nested stacking contexts."


### Q10. [CSS] 兄弟选择器
如果我们要选中当前元素 **之后** 的紧邻兄弟元素，应该用哪个符号？如果我们要选中当前元素 **之前** 的兄弟元素，传统的 CSS 能做到吗？在现代 CSS 中我们如何实现类似“根据子元素状态改变父元素样式”的逻辑？

**答案**: `~` chooses all following siblings, while `+` only the one next behind itself. To select preceding siblings, use `:has(+ div)`， which is only available in modern CSS.

> 💡 **解析**：
> **✅ 答对啦！**
> **专业表达**: "Use `+` for the immediate next sibling and `~` for all subsequent siblings. To select a preceding sibling or style a parent based on its child's state, use the modern `:has()` pseudo-class (e.g., `div:has(+ span)`)."


### Q11. [DRF] Serializer 验证顺序
在 DRF 执行 `is_valid()` 时，这四个验证步骤的先后顺序是怎样的：`validate_<field_name>` (单字段验证), `validate` (多字段交叉验证), `to_internal_value` (类型转换), 以及 Model 层面的唯一性校验？

**答案**: The sequence is as follows:
1. `to_internal_value`
2. `validate_<field_name>`
3. `validate` multi-field cross validation
4. Model-layer validation

> 💡 **解析**：
> **✅ 完全正确！**
> **专业表达**: "The logic follows a flow from **raw data** to **cleaned object**: `to_internal_value` (data parsing) -> `validate_<field>` (field-level) -> `validate` (object-level) -> `UniqueValidator` (database constraints)."

   

### Q12. [Django/Security] SECRET_KEY
Django 的 `SECRET_KEY` 如果泄露，黑客通常能通过它实现最致命的攻击是什么（涉及 Session 签名或密码重置 Token）？

**答案**: If the `SECRET_KEY` is exposed, the hacker can have as many validated tokens as they want. 

> 💡 **解析**：
> **✅ 答对啦！** 核心是**伪造签名**。
> **专业表达**: "A leaked `SECRET_KEY` allows attackers to **forge cryptographic signatures**. They can hijack sessions, generate valid JWTs, or forge password-reset tokens, leading to full system compromise."

### Q13. [Frontend] Polling vs WebSockets (Polling UX)
在实现“等待后端处理结果”时，相比于昂贵的 WebSockets，Short Polling (短轮询) 在极简架构下的主要优势是什么？为了让轮询的 UX 更好，前端通常需要做哪些控制（防止请求堆积）？

**答案**: WebSockets require complicated configurations. Short polling does not, though with higher expenses. The front end should adopt a solution to make its polling frequency longer as time goes by, even just stop trying when the attempts arrive at a certain number.

> 💡 **解析**：
> **✅ 答对啦！** 
> 这种策略叫 **Exponential Backoff (指数退避)**。
> **专业表达**: "Short polling is **stateless and easier to implement**, requiring no persistent connection management. To enhance UX, frontend should implement **exponential backoff** (increasing the delay between requests) and set a maximum retry limit."
