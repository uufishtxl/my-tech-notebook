### Q1. [Django/DRF] serializer.data 与 Model 实例的鸿沟
在 DRF 中，为什么不能直接将 `serializer.data` 作为一个完全等价于 DB Model 实例的对象来看待？通过 serializer 保存的数据主要受到什么契约的限制？

**答案**: `serializer.data` 受到契约白名单的约束，并不会提供和 Model 一样的数据。另外， 回顾一下之前遇到的一个问题，`serializer.data`在 `serializer.save()`之后补充的数据。比如我们的代码内，在保存 Article 实例后，又对文章的 HTML 进行了处理，并将段落文字添加到 Paragraph Model中，而因为这些发生在 `serializer.save()`后，所以 `serializer.data`并不会包含 `paragraphs`这个字段。

> 💡 **解析**：完全正确。`serializer.data` 的内容严格受控于声明的 `fields`（白名单契约）。如果你在 `save()` 后产生了一些衍生数据，但这些字段并没有在 `fields` 中声明，那么它们绝不会自动出现在返回的 `serializer.data` 中。

### Q2. [Tiptap/Vue] 节点属性扩展
在自定义 Tiptap 节点属性时，`addAttributes` 里的 `parseHTML` 和 `renderHTML` 分别负责什么阶段的转换工作？

**答案**: `parseHTML`可以将 `DOM Tree` 中的属性解析到 `JSON` 数据中。`renderHTML`将`JSON` 数据又可以将这些信息再还原到 `DOM Tree`。

> 💡 **解析**：正确。`parseHTML` 负责将外部输入的 DOM 元素转换为 Tiptap 内部的 JSON 状态；`renderHTML` 则负责将内部状态渲染为最终呈现的 HTML。

使用 Tailscale 或 Wireguard 等工具进行内网穿透时，其相比于直接公网端口映射（如传统 DDNS + 路由器端口转发）最大的安全优势是什么？

### Q4. [Django/Models] null=True vs blank=True 规范
在 Django Model 中定义一个字符串类型字段（如 `CharField`）时，官方及社区规范通常极力强调 "不要设置 `null=True`"，请解释这是为什么？`blank=True` 又是管什么的？

**答案**: 因为如果设置 `null=True`，意味着前后端逻辑都需要频繁双重检测是否为空或者空字符串两种情形。`blank=True`允许空字符串，当前端没有提供这个字段，会自动填入一个空字符串。

> 💡 **解析**：正确。在 Django 中，如果字符串字段允许 `null=True`，就意味着数据库里会同时存在 `NULL` 和 `''`（空字符串）代表“没有数据”，这会在查询和逻辑判断中带来巨大的麻烦。`blank=True` 则是表单验证层面的概念，允许输入为空，并在保存时自动填入空字符串。

### Q5. [DRF/ViewSet] get_object() 内幕
在使用 DRF ViewSet 的Detail View时，手动调用 `self.get_object()` 除了去获取数据库记录之外，它内部还会自动执行哪些安全防范与校验处理？

**答案**: 如果发现404错误之类的，可以借助 DRF 的全局错误处理机制来返回错误信息。

> 💡 **解析**：❌ **只答对了一半，答错重置回 Box 1！** `get_object()` 除了封装 `get_object_or_404`，最重要的设计是它在返回对象之前，会自动调用 **`self.check_object_permissions(self.request, obj)`** 进行对象级权限校验。如果直接用 ORM `Model.objects.get()` 就会漏掉这一层极其重要的安全检查。

### Q6. [Vite/DevOps] Proxy & Localhost 帮定陷阱
在使用 Vite 启动本地开发服务且配置了 Proxy 时，如果出现 `localhost` 环境下接口代理成功，但局域网环境下用本机 IP 访问同一个页面却访问失败（比如 404 或代理无响应），一般是什么网络绑定原因导致的？

**答案**: 有个错别字，应该是“绑定”。啊，这里我脑子里开始打架了。我想想所以之前会混淆的几个知识点。一个是写localhost，可能会被 IPv6 解析成一个特殊格式的地址，所以最好是直接写出地址。应该是这个原因？
  
我记得 CORS，开发环境完全可以用 VITE 代理来规避，NODE.JS 会开一个微服务器，将前端的请求转发至后端，因为是后端和后端之间的通信，所以完全不会被浏览器CORS Policy 拦截，那和这个问题没有关系。但是如果 VITE Proxy 代理的 target 写的是 localhost，就可能因为刚才这个 IPv6 的原因出现问题。
  
还有个比较混淆的 ALLOWED_HOSTS 是防止头部攻击。是说 HOST 可以伪造，如果被黑客伪造了，而后端没有做允许白名单，就可能以为这就是自己的域名，在一些密码修改下埋下安全隐患。

还有个 CSRF 的攻击，是和 SessionAuthentication 有关的，和这个问题也没关系。

> 💡 **解析**：理解正确！就是因为 Node 服务器在尝试解析 `localhost` 时，由于操作系统的行为，可能会优先绑定到 `::1` (IPv6)，而后端的服务若是只监听了 `127.0.0.1` (IPv4)，就会导致局域网访问或代理失败。明确写 `127.0.0.1` 能避免该陷阱。

### Q7. [System Design] Database Ordering (Fractional Indexing)
在实现“自由拖拽排序”（比如调整切片序号或者 Kanban 看板卡片位置）功能时，如果直接使用连续的整数 `order` 字段来排序，每次中间插入时往往会导致后续兄弟节点的 `order` 全部被迫更新。请问使用 Fractional Indexing（分数索引）机制是如何优雅解决这个灾难性性能开销的？

**答案**: 比如在 32 和 33 之间插入一条新的数据，通过分数索引，建立一条 order 是 32.5 的数据，就可以在完全不修改任何其它数据的 `order` 值的情况下，优雅地解决灾难性性能开销，同时可以达成目的。

> 💡 **解析**：完全正确。这就是 Lexical/Fractional Indexing 设计的核心，可以完美将拖拽重排的数据库开销从 $O(n)$ 降低到 $O(1)$。

### Q8. [Vue] Ref vs Reactive Reassignment (Proxy pointers)
在 Vue3 中，如果我们将一个新的对象直接粗暴赋值给用 `ref` 和 `reactive` 定义的变量（例如：`myRef.value = newObj` 和 `myReactive = newObj`），它们在响应式系统上各自会导致什么截然不同的后果？

**答案**: `myRef` 仍然保持 Reactivity，因为它被一个安全的 Proxy 包裹着。而 `myReactive` 失去了 Reactivity，因为它被重新赋值为一个普通的对象。

> 💡 **解析**：正确。`myRef.value = newObj` 触发的是 RefImpl 实例的 setter，Vue 框架会在内部重新处理响应式映射。而 `myReactive = newObj` 只是改变了 JavaScript 变量的内存指向，完全脱离了原来的 proxy 对内存地址的监听，失去了响应式。

### Q9. 🆕 [Django/DRF] ViewSet隐式分页陷阱
*(结合刚才的音频切片上一局/下一局跳转 Bug)*
当我们在前端想要请求整个列表（如同一个剧集下的所有切片）并在浏览器端自己执行一次完整的 Map 或 Sort 操作时，往往会遭遇找不到元素的崩溃。DRF 后端的隐式全局分页在这种场景下扮演了什么背刺角色？如果要强行在该接口关闭分页，以确保前端拿到“宇宙全图”，在 ViewSet 中应加上哪行代码？

**答案**: 因为我们的全局设置中设置了分页，DRF 会返回非常刻板的第一个分页的内容。如果当前的内容不在其中，就会发生错误。通过在 ViewSet 中加入`paginaltion_class= None`，就可以关闭这个接口的分页。

> 💡 **解析**：正确。隐式全局分页导致接口默认被切片，返回的是包含 count, next, results 的 Pagination 结构。加上 `pagination_class = None` 可以为该接口关闭分页，保证前端一次性拿到全量数据。

### Q10. 🆕 [API Design] POST/PUT/PATCH 甄别与打破语义迷信
在设计 REST API 遇到复杂的“非标准实体操作”（例如刚才我们对音频切片批量修改的高级操作），很多人会受到“更新必须是 PUT/PATCH，创建才是 POST” 的词法约束。事实上，判断该使用什么请求动词最重要的“工业级判断契约”（比如幂等性考察）是什么意思？为什么很多负责状态流转或批量操作的端点，最终都会乖乖改用 POST 比较安全？

**答案**: 目前我能想到两个考量因素：
1. 操作是否是幂等的。如果不是幂等的，比如我们昨天做的更新 ReviewCard 状态的情形，就必须用 `POST`。
2. 操作是否有违 REST 的原则。比如我们的 Save All Changes 的 操作，如果是 Update 的情况，好像是 PUT 或者 PATCH，而不是创建新的数据，但是因为有违 REST 的原则，因此仍然用了 `POST`。

> 💡 **解析**：完全正确。幂等性（Idempotency，不管发一次还是多次请求，最终系统的状态是一样的）是决定性的。例如“更新状态机的流转动作”或“带有副作用的复杂的批量修改”，直接退回使用 `POST` 是互联网业内普遍且最安全的做法（不强行纠结所谓的 REST 语义）。

## 🌟 今日新知 (New Knowledge)

### 1. 隐式分页陷阱 (`pagination_class = None`)
- **知识点**：在使用 DRF 时，一旦在 `settings.py` 后端全局开启了分页配置（如 `PageNumberPagination`），所有的 `ListModelMixin` 都会受到影响而变成只返回首页数据结构（包含 `next/previous/results` 等）。对于前端需要全量数据来进行客户端排序或上一局/下一局跳转分析时，这会变成隐藏的很深的一个大坑。
- **解决方案**：在指定的 ViewSet 当中，单独设置类级变量 `pagination_class = None` 来局部单独屏蔽全局的分页设定，以此安全的得到数组形态的“全量集合”。

### 2. API Design：打破 "POST就是创建" 的语义迷信
- **核心原则**：在真实的工业级研发当中，经常遇到无法用单纯的表实体 `Update`（PUT/PATCH）衡量的操作接口（如关联状态流转、一次过保存各种混杂的嵌套数据等），最核心审核的点叫做“操作是否幂等”。
- **实践指南**：如果你执行一件事两次会有不同的结果或者累积效应，或者该操作超出了某一个具体实体的作用域边界，不要纠结所谓的词法规定，果断使用代表“处理和运算”含义的万金油 —— `POST` 动词！
