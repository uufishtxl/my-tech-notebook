### Q1. [HTTP] 409 Conflict 状态码适用场景
在 RESTful API 中，什么情况下应该返回 `409 Conflict` 而不是 `400 Bad Request`？请举一个在我们的 Lingua Workbench 项目中可能出现的例子。

**答案**: 当资源冲突时。比如 `Drama` Model Instance 的 `name` 键是唯一键。当 A 用户建立了名为 Friends 的数据后，B 用户也试图创建 Friends，那么就需要返回 `409` 错误。

> 💡 **解析**：✅ **(完全正确)**
> 
> 总结：409 用于“逻辑冲突”（如唯一约束冲突、版本冲突），而 400 用于“语法错误或输入验证失败”。在 Lingua Workbench 中，重复创建同名剧集或同一时间点的切片都是典型的 409 场景。

### Q2. [DRF/Request] request.data 的不可变性
在 DRF 的 View 中，直接修改 `request.data`（例如 `request.data['user'] = 1`）会报错吗？如果需要修改，最优雅且安全的做法是什么？

**答案**: 如果是 JSON 数据 (`application/json`)，是可以的，因为 DRF 会自动将 `request.data`转换为一个 Python 字典。但是如果是表单 (`multipart/form-data`) 就不可以，优雅的做法是使用 `copy()`做一个拷贝数据，然后修改拷贝数据中的键值。

> 💡 **解析**：✅ **(深度准确)**
> 
> 关键在于 `QueryDict` 的 `_mutable` 属性。表单数据解析为 `QueryDict` 时默认不可变。虽然 JSON 数据是普通 dict，但为了代码的一致性与防御性编程，**永远推荐使用 `request.data.copy()`**，这样无论前端传什么 content-type，后端逻辑都能兼容。

### Q3. [Django/ORM] 外键查询性能与语法
`filter(fk_id=1)` 和 `filter(fk__id=1)` 在查询效果上是一样的。但在底层执行和性能上，两者有细微区别吗？推荐用哪种？

**答案**: 底层来说，使用 `filter(fk__id=1)`其实也会被智能地通过 `fk_id` 去匹配。推荐直接用 `filter(fk_id=1)`

> 💡 **解析**：✅ **(完全正确)**
> 
> 虽然 Django ORM 非常聪明，但在 `fk_id` 已经存在于当前表（作为数据库字段）的情况下，直接用 `fk_id` 可以减少一层 ORM 对双下划线语法的解析开销。在某些复杂查询中，滥用双下划线可能会导致不必要的 `JOIN`，养成精确指向字段的习惯更好。

在 Serializer 中定义了 `read_only_fields = ['created_at']`。
1. 如果通过 API 发送 POST 请求包含该字段，DRF 会如何处理？

### Q5. [DOM/Vue] getBoundingClientRect() 的坐标参考
`element.getBoundingClientRect()` 返回的 `top` 和 `left` 是相对于什么的坐标？在实现“滚动监听（Scroll Spy）”或“浮层定位”时，通常需要结合哪个属性来计算绝对位置？

**答案**: 是相对于视口顶部/左部的偏移量。结合 `window.innerHeight`。

> 💡 **解析**：❌ **(核心属性记混了)**
> 
> `top/left` 确是相对于**视口（Viewport）**。但在计算绝对位置（如标记在长页面中的绝对坐标）时，由于视口坐标随滚动变化，你真正需要结合的是 **`window.scrollY`** (或 `pageYOffset`)。
> **公式**：`绝对 Top = rect.top + window.scrollY`。

### Q8. [Django/Security] ALLOWED_HOSTS 的作用
在 `settings.py` 中配置 `ALLOWED_HOSTS = ['*']` 在生产环境下是非常不安全的。它主要是为了防御哪种类型的攻击？

**答案**: Header Host 攻击。具体叫啥来着，就是通过在 Request Header 中篡改 Host 发起的攻击。

> 💡 **解析**：✅ **(完全正确)**
> 
> 正确名称叫 **Host Header Injection (Host 头部注入)**。黑客可以通过篡改 Host 头，诱导服务器生成错误的密码重置链接、重定向到钓鱼站点，或者绕过某些安全策略。

### Q10. [New Knowledge] DRF 全局分页的“退化”处理
在 `ScenarioSelector.vue` 中，我们遇到了后端返回 `{ results: [...] }` 而不是 `[...]` 导致前端报错的问题。如果你不想修改前端代码，想让某个特定接口“退化”为非分页模式，在 ViewSet 层面最简洁的改法是什么？为什么不能只靠 `pagination_class = None`？

**答案**: ？没理解，我们不就是靠 `pagination_class = None`的吗？

> 💡 **解析**：❌ **(这是个进阶坑)**
> 
> `pagination_class = None` 只是去掉了分页逻辑。但如果你的 ViewSet 依然在 `settings` 中受全局分页影响，或者你手动调用了 `self.paginate_queryset`，可能会出现预期外的行为。
> **最稳妥/简洁的退化姿态**：在 ViewSet 中重写 `def paginate_queryset(self, queryset): return None`。这样无论全局设置如何，这个接口都会强制关闭分页，返回原生 Array。

## 🌟 今日新知 (New Knowledge)

### 1. Readability.js 后端集成要点
- **JSDOM 仿真**：之所以在 Python/Node 后端处理抓取时必须用 `JSDOM` 或类似的库，是因为 Readability 的算法需要遍历 DOM 节点。
- **内存管理**：在服务端批量处理时，JSDOM 实例如果不显式 `close()` 或销毁，极易造成严重的内存泄露。

### 2. DRF 分页的“防御性退化”
- **背景**：在前端组件（如 ScenarioSelector）强依赖后端返回 Array 而非 Object `{results: []}` 时。
- **实战**：除了 `pagination_class = None`，如果想更彻底地切断分页逻辑，可以利用 DRF 的钩子：
  ```python
  class ScenarioViewSet(viewsets.ModelViewSet):
      def paginate_queryset(self, queryset):
          return None  # 核心：直接返回 None，彻底禁用分页
  ```
- **价值**：这种做法比修改全局配置或每个前端组件更稳健。
