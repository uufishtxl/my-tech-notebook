### Q1. [DRF/Serializer] validators = [] 的使用场景
在 DRF 中，如果你需要通过 Serializer 进行批量 `update_or_create` 操作，通常需要显式设置 `Meta.validators = []`。为什么要手动关闭 Serializer 的表层唯一性校验？如果不关闭会遇到什么逻辑死锁？

**答案**: 因为批量更新的时候，如果不关闭表层唯一性校验，直接会发生“唯一性”冲突。

> 💡 **解析**：
> **✅ 答对啦！**
> 1. **核心原因**：`Serializer` 的 `UniqueValidator` 看到数据库中已有同名/同 ID 记录时，会直接在 `is_valid()` 层面拦截。
> 2. **逻辑死锁**：如果目的是 `update_or_create` (有则更新，无则创建)，表层校验会直接报错，导致“更新”逻辑永远无法到达底层的 `save()` 或 `.bulk_create()` 方法。


### Q2. [Windows/DevOps] python -m 绕过执行策略
在 Windows 环境下，直接运行全局安装的命令行工具（如 `venv\Scripts\activate` 或某些 CLI）有时会因为 PowerShell 的“脚本执行策略 (Execution Policy)”被拦截。为什么使用 `python -m <module>` 这种方式可以绕过这个限制？

**答案**: 因为使用的是 Powershell 信任的的 python.exe，`module`只是作为一个字符串传入命令中。

> 💡 **解析**：
> **✅ 答对啦！**
> **专业表达**: "It's because `python.exe` is a trusted binary. Passing `-m module` allows **Python internally** to resolve and execute scripts, effectively bypassing PowerShell's external script execution checks on `.ps1` or `.bat` files."

在使用 LangGraph 绑定工具（bind_tools）时，如果某些参数是可选的（Optional），但在提示词中没有被明确提及，LLM 可能会填充默认值。我们如何通过类型定义（TypedDict 或 Pydantic）和参数描述来确保工具调用的灵活性？

**答案**: 用 TypedDict 和 Pydantic 来说明字段的可选属性？我不知道啊，之前不是都是考必须要在提示词中说明吗？你这么问我不知道。

### Q4. [Django/Database] 复合索引 (Meta.indexes) 与单字段 db_index 的选择
什么情况下你应该放弃在多个字段上分别加 `db_index=True`，而改为在 `Meta.indexes` 中定义一个复合索引？请描述“最左匹配原则”对查询性能的影响。

**答案**: 要建立一个复合索引，且单个索引并没有价值的时候。如果在多个字段上分别加上 `db_index`，对查询性能开销会增大。

> 💡 **解析**：
> **✅ 基本正确。** 
> 补充关键细节：
> 1. **最左匹配原则**：复合索引 `(A, B)` 可以覆盖 `A` 的查询和 `A+B` 的查询，但无法覆盖单独 `B` 的查询。
> 2. **选择时机**：当你的 `WHERE` 子句经常同时包含 `A` 和 `B` 时，复合索引比两个独立索引效率高得多，因为它能一次性过滤数据。


### Q5. [Architecture] N+1 Problem (select_related vs prefetch_related)
在 Django ORM 中，`select_related` 和 `prefetch_related` 的底层实现（SQL 层面）有什么本质区别？对于 `ForeignKey` 和 `ManyToManyField` 分别应该使用哪一个？

**答案**: `ForeignKey`用 `select_related`；`ManyToManyFields`用 `prefetch_related`。

> 💡 **解析**：
> **✅ 答对啦！**
> 1. **底层核心**：`select_related` 执行的是 SQL `JOIN`（一张大表，一次查询）；`prefetch_related` 执行的是 `IN (...)`（多张表，多次独立查询并在 Python 中合并）。


### Q6. [Django] update() vs save() 信号
执行 `MyModel.objects.filter(id=1).update(status='done')` 时，Django 的 `post_save` 信号会被触发吗？为什么在需要保证数据一致性的逻辑（如更新缓存）时，这种行为是一个常见陷阱？

**答案**: 不会触发 `post_save`信号。不理解后半句。

> 💡 **解析**：
> **✅ 答对啦上半句！** 补充陷阱：
> 1. **原因**：`.update()` 同步的是原始 SQL 语句，绕过了模型实例的 `.save()` 方法，导致所有基于 Python 层面定义的信号 (Signals) 和 `auto_now` 属性都会失效。
> 2. **陷阱**：如果你依赖信号来 **清理分布式缓存 (Redis)**，导致你在 SQL 更新了数据库后，缓存依然是旧数据。


### Q7. [API] Idempotency (幂等性)
请分别解释 `PUT` 和 `PATCH` 在 RESTful 规范中的语义差异。为什么我们说 `PUT` 是幂等的，而 `PATCH` 在某些非标准实现中可能不是幂等的？

**答案**: `PUT` 是整个数据的替换，因此是幂等的。而 `PATCH`比如在更新次数时，虽然是部分更新，但是结果却不是幂等的。

> 💡 **解析**：
> **✅ 答对啦！**
> **专业表达**: "`PUT` is **idempotent** because replacing a resource with the same state multiple times results in the same outcome. `PATCH` can be non-idempotent if it involves **incremental operations** (e.g., `{ "op": "add", "path": "/count", "value": 1 }`)."


### Q8. [DRF] SerializerMethodField
当我们使用 `SerializerMethodField` 时，默认对应的处理函数名是什么？这种字段在 API 文档生成（如 Swagger）时，通常会遇到什么类型推导问题？如何解决？

**答案**: 是 `get_<field_name>`。后半题不会。

> 💡 **解析**：
> **✅ 答对啦上半句！** 后半句解决：
> 1. **痛点**：由于是动态方法，Swagger 无法通过静态分析得知返回值的类型（默认为 String 或 Unknown）。
> 2. **解决**：在方法上方使用 `@extend_schema_field(MySerializer)` 或在字段定义中显式指定类型。

### Q10. [Regex] Greedy vs Non-Greedy (正则贪婪性)
表达式 `<div>.*</div>` 匹配字符串 `<div>A</div><div>B</div>` 时会得到什么结果？如何通过修改一个字符将其变为非贪婪匹配以只匹配第一个 `div`？

**答案**: 会从头匹配到尾。可以用非贪婪匹配 `<div>.?</div>`。

> 💡 **解析**：
> **❌ 哎呀，翻车了！** 
> 1. **匹配点**：`.?` 表示匹配 0 或 1 个字符，无法覆盖内部的文本。
> 2. **正确解法**：`<div>.*?</div>`。那个 **问号** `?` 紧跟在量词 `*` 后面，才是指示引擎不要贪婪，尽快结束匹配。
