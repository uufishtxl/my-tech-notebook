### Q1. [New: LangGraph/Core] bind_tools 的作用与 ReAct 原则
在 LangChain/LangGraph 中，调用 LLM 时使用的 `bind_tools()` 到底起到了什么关键作用？它和 ReAct (Reasoning and Acting) 模式的核心理念有什么联系？

**答案**: `bind_tools` 会将可用的工具的名称、Docstring等以JSON字符串的形式提供给 LLM，供 LLM 选择。这也就是 ReAct 的 Reasoning 的部分，之后就可以通过 ToolNode 来调用具体的工具，也就是 Act。执行完成后，结果会封装到 ToolMessage 并再次提交给 LLM，让它决定下一步做什么。这就是整个 ReAct 模式在 `bind_tools` 和 `ToolNode` 中的体现。

> 💡 **解析**：**[x] 完美！** 答得非常透彻。`bind_tools()` 的核心本质就是把 Python 函数翻译成大模型能看懂的 **OpenAI JSON Schema** 格式注入到 prompt 底层。它赋予了模型 "Reasoning"（思考是否需要调用工具，以及参数填什么）的能力，而真正的执行 "Acting" 则是交给了外层的 `ToolNode`。

### Q2. [New: FastAPI/Pydantic] `Annotated` 之所以流行 (依赖注入与字段验证引擎)
现代 Python 框架 FastAPI 和 Pydantic 大量推荐使用 `Annotated` 语法。请简述 `Annotated[T, Metadata]` 这个结构的意义，并举出一个在 FastAPI 或 Pydantic 里的典型用例（它代替了传统的什么写法？）。

**答案**: `Annotated` 提供给了现代框架数据的一些原信息（`metadata`），从而能够将一些验证机制提供给这些框架。写我写不出来，我就记得如果不用 Annotated，如果定义一个 age 字段的，验证机制会写得非常反直觉（用 Query），但是用了 Annotated，就非常顺应自然思维，类似 `age = IntegerField(gt=0)`

> 💡 **解析**：**[x] 概念正确！** 
> 它的核心结构 `Annotated[实际类型, 附加元数据]` 让类型提示 (`typing`) 和业务逻辑实现了优雅的解耦。
> 传统的做法经常违背直觉，比如 FastAPI 以前要写 `q: str = Query(default="...", min_length=3)`，把本该放默认值的地方被一个函数占据了。
> 用了 Annotated 后变成了：`q: Annotated[str, Query(min_length=3)] = "..."`，严格保住了 `=` 后面的默认值语义！

### Q3. [Vue] Ref vs Reactive Reassignment (Proxy pointers)
在 Vue 3 开发中，如果你定义了 `let state = reactive({ count: 1 })`，随后在接口请求后执行重赋值 `state = { count: 2 }`，会发生什么后果？为什么？如果一定要整体替换数据，更推荐怎么改写？

**答案**: `state` 将被指向一个普通对象的引用地址，完全失去了 Reactivity。更推荐用 `ref` ，而不是 `reactive`，`ref` 始终被 `Ref` 封装，即便实现 `ref.value` 更新值，也不会失去 Reactivity。

> 💡 **解析**：**[x] 完全正确！** 重赋值会改变变量的内存地址指向，丢掉原来的 Proxy 包装。这也是为什么在涉及数据整体覆盖时（比如接收 API 返回值），`ref` (通过 `.value` 重赋值) 比 `reactive` 更加稳定且不容易出错。

### Q4. [System Design] Database Ordering (Fractional Indexing)
什么是 Fractional Indexing（分数索引 / 浮点索引）？它主要被用来解决数据库业务中什么极其常见的场景和痛点问题？

**答案**: 当需要插入某个新数据时，可以通过分数索引/浮点索引完成，避免了大批量修改数据的工作。

> 💡 **解析**：**[x] 核心痛点抓准了。** 它是干掉“批量修改（Cascading updates）”的利器。特别是在“拖拽排序 (Drag & Drop)”这种场景下，只需要计算 `(前置节点 order + 后置节点 order) / 2`，就能生成一个新的浮点数存入数据库，O(1) 解决排序更新，避免了传统整数排序牵一发而动全身的问题。

### Q5. [Frontend] Polling vs WebSockets (Polling UX)
如果我们在前端需要追踪某个后端异步任务（比如 LLM 抓取文章）的进度，短轮询 (Short Polling) 和 WebSockets (长连接) 各有什么优缺点？为什么有时候一个简单的 Polling 会是更好的架构选择？

**答案**: 短轮询需要每过几秒就发出请求，三次握手，开销非常大，但是胜在简单方便。而Websocks的缺点是需要进行专门的配置，但是优点是一旦建立，一条高速的 TCP 通道也就畅通无助了。

> 💡 **解析**：**[x] 回答得很棒！** WebSockets 虽然是“完美解”，但引入了状态机、断线重连、Nginx 反代配置等极其巨大的基础设施心智负担。而对于简单的异步进度条（例如我们等大模型跑完的一分钟），写一个 `setInterval` 去捞状态接口，开发成本极低，且在这个上下文中这点三次握手的资源消耗几乎可以忽略不计。

## 🌟 今日新知 (New Knowledge)

### 1. Tiptap 的 HTML 序列化双摄机制 (`parseHTML` vs `renderHTML`)
Tiptap（底层是 ProseMirror）有两套模型：自己内部管理的 **JSON 树**，以及渲染在浏览器里的 **DOM 树**。
- `parseHTML`: **"读入"** 阶段。当 Tiptap 刚刚初始化（`setContent` 传来一段 HTML 字符串），或者用户从外部粘贴内容时触发。它负责到对应的 DOM 标签身上，用原生的 `element.getAttribute('data-pid')` 把值抠出来，存进内部 JSON 模型里。如果这里没写，你的初始属性全会丢失。
- `renderHTML`: **"写出"** 阶段。当 Tiptap 渲染内部 JSON 模型到浏览器真实的 DOM 树时触发。它负责把你刚才存下来的内部属性，组装成 `{ 'data-pid': value }` 字典，最后变成 `<p data-pid="123">` 显示在页面上。

### 2. 万恶的 `getBoundingClientRect()` 坐标系
记住一句话：**Client = 可视区域 (Viewport)**。
所以 `getBoundingClientRect().top` 永远是相对于**浏览器屏幕当前的顶边**的，而不是整个长网页的绝对顶部。

**为什么它非常适合用来做防网页大纲的“导航监听 (Scroll Spy)”？**
因为当你在页面里滑动 `scroll` 事件时，你只需要在循环体去 `if (rect.top <= 指定阈值，比如 250px)`：
- `>250` 代表这个段落还在屏幕下面，没读到。
- `<=250` 代表这个段落已经“顶破”视阈线，进入到了黄金阅读区上方，这时候就可以高亮左侧相应的 Outline 大纲红点了。
- 而如果是相对于整个 document，你还得去拿 `window.scrollY` 进行相减或相加运算，极其繁琐。

> 🖼️ **[绝妙的记忆心智模型]**
> 把长网页想象成一张**《清明上河图》**长卷，而你的屏幕就是一个 **40x20CM 的固定透明玻璃框**。
> - `offsetTop`：绝对位置。画中某个人物距离画卷最左侧/最顶端的物理距离。
> - `getBoundingClientRect().top`：相对位置。画中这个人物，距离我们这块**透明玻璃框**顶部的距离。
> 如果用 `offsetTop` 算，还得拿画卷目前卷了多少（`window.scrollY`）进行加减，非常别扭；而 `getBoundingClientRect()` 直接告诉你他现在在玻璃框里的哪个位置，简单直接！
