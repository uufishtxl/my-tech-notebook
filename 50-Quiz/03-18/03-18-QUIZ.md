### Q1. [Box 1] Django/DRF: read_only_fields 的防御边界
在 DRF 的 Serializer 中定义了 `read_only_fields = ['created_at']`。这主要拦截的是哪个层面的写入？如果我们在后端的 ViewSet 中直接调用 ORM 的 `Model.objects.create(created_at='2026-03-18')`，这个字段会被限制写入吗？为什么？

**答案**: 拦截客户端的写入。不会被限制。因为只是拦截客户端。

> 💡 **解析**：✅ **(完全正确)**
> 
> 明确了这一点非常重要：`read_only_fields` 只是 **API 层的契约约束**，它是通过控制 Data Intake (反序列化) 来实现的。它完全不保护数据库层，也不限制后端的内部逻辑。如果你需要数据库级的只读，应该使用 `editable=False`。

### Q2. [Box 1] DOM/Vue: getBoundingClientRect() 与视口定位
昨天的错题复盘：`element.getBoundingClientRect()` 返回的 `top` 和 `left` 是相对于什么的坐标？如果我们要计算哪怕页面发生滚动后，该元素在整个 Document 中的“绝对高度（绝对 Top）”，正确的计算公式是什么？

**答案**: `绝对 Top = rect.top + window.scrollY`

> 💡 **解析**：✅ **(完全正确)**
> 
> 克服了昨天的盲区！`top` 是相对于视口（Viewport）的，而随着滚动，页面已经延伸的部分（`window.scrollY`）必须加回来，才是相对于整个 Document 顶部的绝对位置。

### Q4. [Box 1] Backend/Extract: Readability.js 与 JSDOM 的共生关系
为什么在 Node.js 或 Python (如使用 PyExecJS) 后端环境中运行开源的 `Readability.js` 来提取正文时，必须引入 `JSDOM`？它在其中扮演了什么角色？

**答案**: 因为需要抓取 DOM，但是Node.js本身并没有DOM，所以需要引入 JSDOM 来模拟出 DOM Tree 和 Windows 对象。

### Q5. [Box 2] DRF/Response: 201 Created 的 Location 响应头去哪了？
按照 REST 规范，当你成功 POST 创建一个资源后，服务端除了返回 `201 Created` 状态码，通常还应该在响应头（Response Headers）中返回一个什么字段来指示新资源的位置？DRF 默认有实现这个行为吗？

**答案**: `location`字段。实现了吧，但是如果重写 `create`，就需要手动完成。

> 💡 **解析**：✅ **(完全正确)**
> 
> 在 DRF 的 `CreateModelMixin` 中，底层会尝试获取 `instance.get_absolute_url()` 或根据路由生成链接放入 `Location` 头。如果自定义 `create` 且不调用 `self.get_success_headers(serializer.data)`，这个规范就会被打破。

### Q6. [Box 2] DRF/ViewSet: get_object() 内幕
在 DRF 默认的 `get_object()` 执行流程中，**权限校验** (`check_object_permissions`) 和 **对象获取** (`get_object_or_404`) 谁先谁后？这种顺序设计的核心安全考量是什么？

**答案**: `get_object_or_404`先，`check_object_permission`后。为了杜绝黑客试探账号对资源的访问权限。

> 💡 **解析**：✅ **(深度思考)**
> 
> 没错。**“先查有无，再查能读”**。如果先报 403 (无权)，黑客就知道这个 ID 确实存在；如果先报 404 (无此资源)，就能完美隐藏数据的存在性，这种做法被称为“隐身防御”。

### Q7. [Box 3] API Design: POST/PUT/PATCH 甄别与打破语义迷信 (幂等性判断)
什么是 API 的“幂等性”（Idempotency）？请说明 POST、PUT 和 PATCH 三种 HTTP 方法中，哪些是天然幂等的，哪些不是？

**答案**: `PUT` 是天然幂等的，因为会直接替换整行数据，无论操作多少次，结果都一样。`POST`和 `PATCH`不是天然幂等的。

> 💡 **解析**：✅ **(基本准确)**
> 
> 核心定义是：**多次执行与单次执行的效果是否相同**。
> - `PUT`: 替换。幂等。
> - `POST`: 新增。不幂等（发两次会产生两条数据）。
> - `PATCH`: 增量修改（如 `age = age + 1`）。不幂等。

### Q8. [Box 3] Django/DRF: serializer.data 与 Model 实例的鸿沟
当你拥有一个 Django Model 实例 `obj` 时，为什么不能直接将其当作 JSON 返回，而必须经过 `serializer.data`？这仅仅是为了类型转换吗，还是涉及更深层的架构契约？

**答案**: 也是要转化成符合序列化工具的数据格式吧。不太明白这题要考什么。

> 💡 **解析**：❌ **(核心概念：契约守卫)**
> 
> 不仅仅是格式转换。`serializer.data` 的真正价值在于它由 **`Meta.fields`** 严格定义的 **数据契约（Schema Contract）**。
> 直接返回 Model 实例（假设能转 JSON）会泄露所有数据库字段。Serializer 的作用是手动挑选、隐藏敏感字段，并执行额外的计算（如 `SerializerMethodField`）。它是一个保险柜和过滤器。

### Q9. [New Knowledge] Vue/Component: v-if 的挂载时机与生命周期
在我们的前端项目中，常常使用 `v-if` 来控制子组件的显隐。如果一个子组件由 `<child-component v-if="show" />` 包裹，当 `show` 从 `false` 变为 `true` 时，该子组件的 `onMounted` 生命周期函数会执行吗？当变为 `false` 时，该子组件内绑定的全局滚动事件（如果不手动清理）会自动解绑吗？为什么？

**答案**: 会执行。子组件内绑定，是绑定在子组件的元素上的吗？如果是，会自动解绑。如果是绑定到 windows 全局对象，必须手动清理。

> 💡 **解析**：✅ **(直击痛点)**
> 
> 这就是为什么 `onUnmounted` 里的清理代码如此重要。`v-if` 是摧毁式卸载，组件元素都没了，绑在元素上的监听器会自然消亡。但绑在 `window` 或 `document` 上的幽灵事件会留下来，造成泄露。

### Q10. [New Knowledge] Django/DRF: ValidationError 的状态码映射
当我们在 DRF 的 `Serializer.validate()` 钩子中主动抛出 `serializers.ValidationError("无效的数据")` 时，前端最终会接收到什么样的 HTTP 状态码？为什么 DRF 会选择映射到这个特定的状态码，而不是 `400` 以外的错误码（例如 500）？

**答案**: 不知道

> 💡 **解析**：❌ **(必备常识)**
> 
> 会映射到 **`400 Bad Request`**。
> 原因是：ValidationError 表示的是 **“输入不合法”**，并不是服务器坏了 (500) 或没权限 (403)，所以遵循 HTTP 标准，4xx 系列代表客户端错误，400 是最通用的表达。

## 🌟 今日新知 (New Knowledge)

### 1. 序列化器的数据契约价值
- **隔离性**：永远不要让数据库结构直接暴露给 API。
- **派生性**：通过 Serializer 可以返回模型中不存在的字段（动态计算）。

### 2. Vue 的 `v-if` 与全局泄露
- **卸载原则**：绑在组件 DOM 上的事件 (如 `@click`) 随 DOM 销毁而销毁；但全局 API (如 `addEventListener`, `setTimeout`) 必须手动 `remove` 或 `clear`。

### 3. DRF 状态码哲学
- **400 vs 422**：DRF 默认使用 400。虽然有的 RESTful 倾向用 422 (Unprocessable Entity)，但 400 是兼容性最强的选择。
