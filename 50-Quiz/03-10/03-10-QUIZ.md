## 1. 核心复习 (Review Items)

### Q1. [Arch] API-First & Contract-Driven
什么是“工业级闭环 (Industrial-grade Closed-loop)”开发流？为什么提倡在编写任何业务逻辑代码之前，先通过 Schema 定义好 API 契约？

**答案**: API First + 契约优先。因为约定好后，前端后端可以无障碍地并行开发，而不会因为后面 Schema 冲突需要调整。

> 💡 **解析**：
> **✅ 答对啦！**
> 完全切中痛点。API 契约 (Contract) 充当了“单点真理 (Single Source of Truth)”。定义好 Schema 后，前端可以用 Mock 数据直接起跑，后端安心写逻辑，集成阶段无痛对接，这就是工业级解耦。
> **SRS 进度**：Box 1 -> **Box 2**

### Q2. [API Design] 扁平化关联查询 vs 深层嵌套序列化
当处理深度关联的数据结构设计（如 Drama -> Season -> Episode）时，相比于“在一个巨型 JSON 中深层嵌套序列化返回所有层级数据”，使用“扁平化的查询（配合 Foreign Key 进行过滤查找接口）”在前端灵活性和后端性能（比如对 N+1 防御上）上有哪些核心优势？

**答案**: 如果是要深层嵌套的数据，可能会产生 N+1 查询的问题。比如查询到 `season`后，遍历 `season` 继续去查询 `episodes` 数据深层嵌入进来。而使用扁平化查询，也就是通过 `SELECT IN`查询，就可以避免 N+1 的问题，完全可以1）取出所有符合的 Drama 数据，然后从 `Episode`中取出所有 drama_id 在第一步范围内的数据，就可以避免 N+1了。前端也更好处理扁平的数据。

> 💡 **解析**：
> **✅ 分析得非常透彻！**
> 1. **后端性能**：深层级序列化如果不使用 `prefetch_related` 会导致灾难性的 N+1。而扁平接口中，只吐出列表数据，压力极小。
> 2. **前端灵活性**：扁平化意味着按需加载。你想渲染几个 Season，就调几次请求。不用去递归解包一个臃肿繁杂的巨型 JSON。
> 3. **架构解耦**：每个模块高度正交，缓存失效等场景也更好维护。
> **SRS 进度**：Box 1 -> **Box 2**

### Q3. [DRF/ViewSet] get_object() 内幕机制
当在 DRF 的 ViewSet 中隐式或显式调用 `self.get_object()` 时，其内部究竟执行了哪三个核心步骤（涉及 queryset 过滤、404 处理、权限校验）？为什么是先抛 404，而不是先抛 403 权限不足，这有着怎样的防御意义？

**答案**: 首先会做 queryset 过滤，然后是404处理，最后是权限校验。这么做的防御意义是为了避免黑客刺探账户对资源的访问权限。

> 💡 **解析**：
> **✅ 答对啦！精炼且精准。**
> 顺序：`filter_queryset()` -> `get_object_or_404()` -> `check_object_permissions()`。如果先验证 403，黑客就可以通过状态码区分“资源是否存在”和“我有没有权限”，从而通过遍历 ID 来探视系统的数据量和存在性；先给 404 就直接把刺探路子堵死了。
> **SRS 进度**：Box 2 -> **Box 3**

### Q4. [DRF/Serializer] Read-only 字段的显式与隐式声明考量
既然 Django 中的 `auto_now_add=True` 这样的 Model 属性已经让字段拥有了隐式只读的特性，为什么我们在真实项目协作中，仍被强烈建议要在 Serializer 的 `Meta.read_only_fields` 中显式地把它再写一遍？

**答案**: 因为更易读更容易维护。即便后续开发者做了更改，也不会 break。

> 💡 **解析**：
> **✅ 答对啦！**
> Defensive Programming（防御性编程）的典范。不仅保证了代码的自我解释性（Explicit is better than implicit），还能在 OpenAPI/Swagger 层面稳定生成正确的契约。
> **SRS 进度**：Box 2 -> **Box 3**

### Q5. [API Architecture] 嵌套路由的设计与解耦抉择 (Action vs Filter)
假设你需要查阅某部电影 (Drama) 所包含的各个季度 (Season)。
方案 A：在 DramaViewSet 使用 `@action(detail=True)`。
方案 B：创建一个独立的 SeasonViewSet，透过 `GET /seasons/?drama_id=X` 过滤。
结合“解耦”思想与 API-First 的灵活性，请解释为什么方案 B 往往是业务更成熟的决策？

**答案**: 因为 A 方案里，需要使用到 Season 的 Serializer 来进行序列化，这就有耦合的情况的发生。而使用 SeasonViewSet，就不存在这种“串着用”的情况的发生，并且支持多个 Query Params。

> 💡 **解析**：
> **✅ 完美掌握！**
> 核心就是：不要让 A 关心 B 是怎么组合、序列化的。方案 B 是面向资源的纯粹表达，同时 `Query Parameters` (`?name=abc&sort=-id`) 的扩展性远比被限制在一个 `@action` 函数里强得多。
> **SRS 进度**：Box 2 -> **Box 3**

## 2. 🌟 今日新知 (New Knowledge)

### Q6. [API Design] URL Path 参数 vs Query Parameters 的本质区别
在 RESTful API 最佳实践中，“路径参数 (如 `/users/123/`)”与“请求参数 (如 `/users/?id=123`)”的语义界限究竟在哪？请从“唯一标识定位 (Resource Identification)”和“范围过滤 (Resource Filtering/Sorting)”角度解释在开发 API 时如何正确选取使用这两种方式。

**答案**: 专业名词太多，我不太理解语义界限的意思。我就知道 URL Path，只能支持单一参数。而请求参数可以支持多个参数。后面你那串我也没太明白。

> 💡 **解析**：
> 别急，其实你的直觉已经摸到了边。用大白话解释就是：
> 1. **URL Path 参数 (如 `/dramas/1/`)**：用来 **“精准锁定某一个具体的东西”**。它代表资源层级。当你脑子里想的是“我不确定有没有，我要找特定 ID”的时候，用 Path。这就叫 Resource Identification。
> 2. **Query Parameters (如 `/dramas/?year=2024&ordering=-id`)**：用来 **“缩小范围、排序或筛选批量的东西”**。当你脑子里想的是“符合我这几个条件的一批东西”的时候，用 Query Parameters。
>
> **为什么有这个规定？**
> 因为这样对 HTTP 缓存和网关最为友好。你可以想象 URL Path 是“文件夹路径”，Query 参数是文件夹右上角的“搜索过滤框”。
> **SRS 进度**：新增至 **Box 1**

### Q7. [Vue3/Vite] 自动按需导入 (unplugin-vue-components) 的工程价值
在构建最新的 Vue3 PWA 项目时（例如整合 Element Plus 等 UI 库），过去开发者通常在 `main.ts` 中一键`app.use(ElementPlus)` 全局注册，而现在纷纷选择基于 `unplugin-vue-components` 的依赖按需自动解析注册工具。这对最终上线的 Bundle 体积和前端加载性能有何实质性改变（提示: Tree-shaking 联动效应）？

**答案**: 就是按需加载资源，不需要整个都bundle进来，所谓的 Tree-shaking。答案不就是 Tree-shaking吗？

> 💡 **解析**：
> **✅ 直击要害。是的，答案就是 Tree-shaking 的落地！**
> 全局 `app.use` 会导致打包工具认为整个 Element Plus 库“都被用到了”，因此全盘塞进最后的 JS 产物（可能高达数 MB）。而用了按需加载插件后，打包器如果在模板中只看见了 `<el-button>`，那么它 **只会** 切下 Button 相关的 JS/CSS 塞进产物里，直接让前端首屏渲染体积缩小几个量级。
> **SRS 进度**：新增至 **Box 1**
