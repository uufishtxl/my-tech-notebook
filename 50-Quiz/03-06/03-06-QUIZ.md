### Q1. [DRF/ViewSet] get_object() 内幕：权限校验、对象获取与自动 404 处理
Question: 在 DRF ViewSet 中，调用 `self.get_object()` 的内部流程是怎样的？它是如何结合权限校验（Permission Classes）并自动抛出 404 的？

**答案**: `self.get_object()` 会做两个动作：1. 权限检查 `self.check_object_permission`；2. `self.get_object_or_404()`，也就是如果发现用户没有权限，或者没有发现相关数据，都会通过 DRF 的全局错误处理抛出错误。

> 💡 **解析**：❌ **(答错 - 顺位有误)**
> 
> `get_object()` 的核心动作顺序极其重要：
> 1. 先执行 `get_object_or_404(queryset, **filter_kwargs)` 从数据库获取对象。**如果找不到，直接抛出 404，后续代码不执行**。
> 2. 获取到对象后，才执行 `self.check_object_permissions(self.request, obj)`。
> 3. 如果没权限，抛出 **403 Forbidden**（未登录则 401）。
> **核心防御价值**：这样的顺序是为了**避免泄露数据存在性**。如果先校验权限且报错 403，意味着攻击者能探测出这个 ID 在数据库里存在。先报 404 就可以隐藏它的存在。(打回 Box 1)


### Q2. [Django/DRF] ViewSet 隐式分页陷阱 (pagination_class = None)
Question: DRF ViewSet 中为什么有时 `list` 接口返回的是分页结构，而有时却是纯数组？如何彻底关闭或自定义分页行为？

**答案**: 因为在 `settings.py`中可能对 `REST_FRAMEWORK` 对象内部设置了全局分页 `'DEFAULT_PAGINATION_CLASS': 'rest_framework.pagination.PageNumberPagination'`。如果需要关闭分页，可以在对应的 ViewSet 中设置：`pagination_class = None`

> 💡 **解析**：✅ **(完全正确)**
> 
> 补充：DRF 中的全局分页影响很大。你提到的 `pagination_class = None` 是一种干净利落的”局部退化“策略，可以确保该 ViewSet 的 list 结果永远是一个干净的 Array，这在需要拉取下拉列表全部选项时特别有用。


### Q3. [API Design] POST/PUT/PATCH 甄别与打破语义迷信 (幂等性判断)
Question: 在 REST API 设计中，不应仅仅为了“部分更新”或“创建”的字面含义选方法。请从“幂等性”的角度解释何时必须用 PUT，何时用 POST/PATCH。

**答案**: 从“幂等性”的角度，如果操作不是幂等的，那么用 `POST`或 `PATCH`，如果是幂等的用 `PUT` 。另外，我顺便回顾下之前学的，还有两种情况用 `POST`：
- 如果通过 `@action`装饰器定义的 API 名称是动词，就会是 RPC (Remote Procedure Call)，用 `POST`。
- 如果是批量数据操作，也约定俗成用 `POST`。
另外，这题我翻了LLM小抄：我第一次知道原来 PATCH 也属于“危险操作”，不是幂等的。

> 💡 **解析**：✅ **(完全正确)**
> 
> 总结得很棒！核心判断依据就是“幂等性”。多次执行是否产生不同影响。POST/PATCH 确实不具备天然的幂等性。
> 补充 RPC 和 批量操作选用 POST，说明你吃透了这个知识点。

### Q4. [Vue/Animation] 过渡与 z-index 叠放陷阱 (Teleport & Popper 解决层叠上下文隔离)
Question: 在 Vue 中实现带过渡动画的弹窗组件时，常遇到 z-index 失效被遮挡的问题。为什么 `<Transition>` 常常加剧这种现象？如何通过 Teleport 来完美解决？

**答案**: 因为 `Transition`和用 `filter`（具体是什么 `filter` CSS 属性我忘记了），会自动将元素用一个父级元素来包围起来。这时候子元素就无法突破这个父级元素本身的 `z-index`，因此会出现失效被遮挡的问题。通过 `teloport` 可以将元素放入 body 以下，就可以突破这层限制。

> 💡 **解析**：✅ **(完全正确)**
> 
> 注意你提到的 `filter`：任何非 `none` 的 `transform`、`filter` 或者 `opacity` 不为 1 都会使得浏览器为该元素创建一个**新的层叠上下文（Stacking Context）**，从而把它的子元素困在里面，导致 z-index 无法与外部竞级。`Teleport` 拔出了这把锁！


### Q5. [Frontend/Audio] HTML5 Audio 的就绪判定与 InvalidStateError 防御 (readyState >= 1)
Question: 操作 HTML5 `<audio>` 元素的 `.play()` 或移动 `currentTime` 时，为什么经常会抛出 InvalidStateError？如何使用 `readyState` 来防御此类错误？

**答案**: 因为，可能会在 `metadata`还没有获取到的时候就去试图去操作 `currentTime`，但是这些数据根本还没有加载。如果用 `readyState >= 1`，就保证 `metadata` 已经加载完成，并且可以操作 `currentTime`

> 💡 **解析**：✅ **(完全正确)**
> 
> 没错！Audio 对象只有在 `readyState >= 1` (HAVE_METADATA) 时，它的 `duration` 和各种媒体属性才被载入。在此之前强制设置 `currentTime` 会引发 InvalidStateError 报错。


### Q6. [Prompt Engineering] 针对工具调用的显式路径引导 (Explicit Path Guidance)
Question: 在构建给 Agent 的 Prompt 时，为什么要明确指明工具调用的文件路径或作用域（Explicit Path Guidance）？这对规避 LLM 幻觉有何帮助？

**答案**: 因为大模型本身会倾向偷懒，或者抱有幻觉。因此需要通过提示词明确地指出工具调用的文件路径，适用的场景等指导，并且如果有 Few-shots 就更好了，只有这样，才可以让 LLM 向期望的链路进行路由切换。

> 💡 **解析**：✅ **(完全正确)**
> 
> 幻觉往往来自于大模型根据自己预训练的数据进行“脑补”。显式路径不仅是“告诉它去哪里找”，更是利用物理约束掐断了它的发散余地。

### Q8. [Vue/Events] Global Event Lifecycle (内存泄漏与幽灵触发)
Question: 在 Vue 组件中注册全局事件 (如 `window.addEventListener`) 会带来怎样的生命周期隐患（幽灵触发、内存泄漏）？应如何正确清理？

**答案**: Vue 的组件销毁时，只会自动清理注册在组件内部的事件，而不会去处理注册在全局 `window`上的事件。这就会导致，当组件被多次创建后，就会注册多个同样的事件侦听。一旦触发，多个事件侦听都会工作起来，会造成灾难性的后果。应该通过 `onUnmounted` 钩子通过 `window.removeEventListener('event-name', callback)`来注销通过 `onMounted` 注册的全局侦听。

> 💡 **解析**：✅ **(完全正确)**
> 
> DOM 级事件（尤其是 document, window, body 上挂载的事件）并不跟随 Vue 组件的生命周期被清理，这不仅导致内存泄露，还会带来极其难缠的“幽灵触发（Ghost Triggering）”现象。必须在 `onUnmounted` 一一对应地 `remove`。

### Q9. [DRF/Serializer] Read-only 字段的隐式行为
Question: 某些模型字段（例如外键、文件上传字段）在 DRF 中似乎隐式地具备一定的只读或不可修改特性。我们还需要在 Serializer 的 `read_only_fields` 中显式声明它们吗？显式声明的核心防御价值什么？

**答案**: 对于 `id`、一些 `DateTimeField`(`auto_now_add=True`、`auto_add=True`)字段，以及 serializer 中的关系字段中已经注明是 `read_only=True`，或者这个当这个 serializer 只会用于一个 `ReadOnlyModelViewSet`时，都不需要显示声明到`read_only_fields`。防御客户端来写入或更新这些字段的值。

> 💡 **解析**：✅ **(优秀！)**
> 
> 你的分析证明了你很清楚框架的内在规则。不过，在**工业级**架构中，我们依然提倡：**就算是隐式 read_only，最好也再写一遍到 `read_only_fields` 里面去。**
> 为什么？因为这叫做“Defense in Depth（纵深防御）”和“Contract Explicitness（契约显式化）”。你在 Serializer 层面显式声明，那么即使未来某个队友在 Model 层面手欠改掉了 `auto_now_add`，这个字段在这个 API 里依然受到只读保护。这也方便 Code Review 时一眼看出哪些字段受到保护。


### Q10. [API Architecture] 嵌套路由归属权
Question: 获取“某部 Drama 包含的所有 Seasons”（即 `GET /dramas/:id/seasons/`），在后端架构时，应该归属于 DramaViewSet 的 `@action(detail=True)` 还是归属于 SeasonViewSet 的 `list`（并通过 filter 过滤）？请比较这两种策略的优劣。

**答案**: 应该归属于 `DramaViewSet`吧，路由会是 `GET` `/dramas/:id/seasons`，API 名称 Readibility 高，符合 Restful 设计原则，但是在返回数据时，可能还要再 DramaViewSet 中引入 Season 的 Serializer，会有藕合的风险。
如果是 `SeasonViewSet`，会设计成什么样？`GET` `/seasons/?drama_id=1`。ModelViewSet 中可以解耦。

> 💡 **解析**：✅ **(深度思考！)**
> 
> 你把两者的优劣都分析透了！
> - **`@action(detail=True)` 归属 DramaViewSet**: 路由很漂亮 (`/dramas/1/seasons/`)，也是经典的嵌套资源形式。缺点需要重写 `get_serializer_class` 或引入强耦合，遇到复杂查询、分页容易变成屎山。
> - **归属 SeasonViewSet (`GET /seasons/?drama_id=1`)**: 将资源平行化处理，只需要简单的 `django-filter` 就能利用原生 ViewSet 强大的 `ListModelMixin` 完成搜索过滤。这是**API First** 架构更提倡的弱耦合模型。
> 
> 二者取舍见功力。你的理解非常到位！
