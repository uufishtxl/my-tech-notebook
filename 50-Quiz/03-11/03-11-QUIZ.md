### Q1. [DRF/ViewSet] get_object() 内幕
简述 DRF 中 `get_object()` 的工作流程，它内部是如何进行权限校验以及自动处理 404 异常的？

**答案**: 首先从 QuerySet 中找到匹配的数据，如果发现 Resource Not Found，会抛出404错误。如果匹配到数据，则会进一步检查权限，权限不够时，会抛出401或403错误。

> 💡 **解析**：✅ [正确] 逻辑完全正确。底层逻辑是先拿到对象的 instance，然后执行 `self.check_object_permissions(self.request, obj)` 进行鉴权，通过后再返回。

### Q2. [DRF/Serializer] Read-only 字段的显式与隐式声明考量
在 DRF Serializer 中，什么时候我们需要显式声明 `read_only_fields`？如果不小心遗漏声明，但该字段本身是从属于模型的关联字段（例如在嵌套创建时），会导致什么隐患？

**答案**: 会导致客户端可以写入和修改这些字段。不太明白强调从属于模型的关联字段是为了什么。

> 💡 **解析**：❌ [不完全正确] 强调从属于模型的关联字段，是因为这会导致**越权漏洞**。比如模型里有 `user` ForeignKey，前端如果在 payload 传了 `{"user": 2}`，而你忘了在 Serializer 中配置 `read_only_fields = ['user']` 拦截它，DRF 就会把它强行改掉，导致原本属于张三的资源变成了李四的。安全漏洞尤为严重！(已退回 Box 1)

### Q3. [API Architecture] 嵌套路由归属权 (Action vs Filter)
设计 API 时，对于类似 `/dramas/{id}/episodes/` 这样的请求，什么情况下应该通过给 `DramaViewSet` 添加 `@action(detail=True)` 实现？什么情况下更推荐将它归于 `EpisodeViewSet` 并配合 `django-filter`（例如 `/episodes/?drama={id}`）？

**答案**: 如果 `episodes`并不需要使用一个 `EpisodeSerializer` 来作为序列化工具，并且是一个 `drama` 下的资源，就完全可以在 `DramaViewSet`中实现。反之，如果需要一个别的序列化工具来进行序列化，或者用上述方式会不符合 Restful 设计原则，或者有多个过滤参数，就用后者。

> 💡 **解析**：✅ [正确] 核心理解正确。补充一点：`@action` 比较适合处理真正的**“行为/动作”**（如 `/dramas/{id}/publish`），而涉及到获取下属关联集合（集合往往需要分页、过滤）使用原生的 `ViewSet + Filter` 最为干净清爽。

### Q4. [API Design] POST/PUT/PATCH 甄别 (幂等性判断)
简述 POST、PUT 和 PATCH 在设计 RESTful API 时的核心区别，并解释什么是“幂等性”。

**答案**: “幂等性”是指多次执行导致的结果是一样的。`PUT` 是替换整个 `row`，是幂等的。`POST` 和 `PATCH` 则不是幂等的。

> 💡 **解析**：✅ [正确] 完全正确。PUT 是全量替换（不管执行多少遍，最终状态都是你传过去的那个状态，所以幂等），PATCH 是增量/局部修改（例如累加操作 `amount = amount + 1` 就不幂等）。

### Q5. [Django/DRF] serializer.data 与 Model 实例的鸿沟
获取到模型的 instance 之后，直接拿 `instance.xxx` 和从 `serializer.data['xxx']` 中取值有什么本质区别？为什么使用 `serializer.data` 时返回的字典内容经常与直接操作 Model 实例不同？

**答案**: `instance` 是 `Model`的数据实例。而 `seraizlier.data`受限于在 Serializer 的 `Meta.fields`中声明字段。并且 `Serializer` 还可能有一些字符串转换，甚至一些通过 `get_<field_name>`生成的非 Model 内的字段，因此不能保证一样。

> 💡 **解析**：✅ [正确] 答得非常清晰！Serializer 就是为了在 Model 和 客户端中间起到隔离、转换、补充衍生数据的防火墙作用。

### Q6. [Django/ORM] update() 不触发 auto_now=True
为什么对 QuerySet 直接调用 `.update(...)` 时，模型中声明带有 `auto_now=True` 的时间字段**不会**自动更新？如果需要更新应如何解决？

**答案**: 因为直接调用这个函数，绕过了 Django，直接执行 `UPDATE` SQL 语句。如果需要更新，就在 `update`中提供时间字段；或者不要绕过 Django，而是使用 `save()`。

> 💡 **解析**：✅ [正确] 完全正确！`.update()` 是底层的批量操作，不仅不触发 `auto_now`，所有声明的 `save()` 重写和 `Signals`（信号）也不会被触发。

### Q7. [Django] filter vs get (Exceptions vs Empty)
阐述 `Model.objects.filter()` 和 `Model.objects.get()` 的核心差异，特别是当数据库中**没有匹配记录**或**存在多条记录**时它们的行为分别是什么。

**答案**: `Model.objects.filter()`是执行 `SELECT * FROM`，`Model.objects.get()`执行的是 `SELECT 1 FROM`。如果没有匹配，前者是空的 `QuerySet`，后者是如果没有匹配到任何结果，会Raise Exception，`DoesNotExist`，多个记录则是 `MultipleObjectsReturned`

> 💡 **解析**：✅ [正确] 对于异常情况的描述完全准确。纠错一点：`.get()` 底层其实也是用类似 `SELECT ... LIMIT 2` 去查的（查到两个就知道抛 `MultipleObjectsReturned`），真正的 `SELECT 1 (1作为常量)` 经常是用在 `.exists()` 加速中。但你对返回结果和异常判断的认识是满分的。

## 🌟 今日新知 (New Knowledge)

> 💡 **知识讲解**：
>
> 1. **关于 get_or_create**：
> `get_or_create` 底层是开启了数据库层面的防并发措施的（它通常包裹在一个原子事务里）。它首先进行查找，如果没找到，才会结合查找的参数和 `defaults` 字典生成 INSERT 语句创建新的 row。使用它比你自己手写 `try...except DoesNotExist` 并 `save` 要优雅和安全得多，且返回值会明确告诉你是不是新建的 (`created` 为 Boolean)。
>
> 2. **关于 HTTP 409 Conflict**：
> RESTful 中遇到重复数据（违反唯一性约束）或者资源状态不对（如尝试删除一个正在开机的云主机时），用 `409 Conflict` 拒绝请求是标准操作，因为它明确告诉前端：你的数据格式没毛病（不是 400 Bad Request），单纯是目前服务器里的情况不让你做这件事。遇到 409，通常前端可以提示用户：“该记录已存在”或者“当前状态不能执行此操作”。
