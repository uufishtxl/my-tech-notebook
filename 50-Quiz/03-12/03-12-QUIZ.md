### Q1. [DRF/Serializer] Read-only 字段的显式与隐式声明考量
在 DRF 中，除了在字段上显式声明 `read_only=True` 之外，还有什么隐式的声明方式？这两者的使用场景有什么取舍？

**答案**: 隐式的声明方式？如果是 Primary Key、auto_now_add=True，或者 auto_add=True，就是默认是只读的。或者如果用了 `get_<field_name>`应该也是隐式只读的。用 `Meta.read_only_fields`应该算显示的吧？显示，对易读和可维护性比较有利；如果用隐式，就代码比较干练简洁。
我对这里的显示和隐式不太理解。

> 💡 **解析**：
> 1. **隐式只读**：你提到的 `PK`、`auto_now_add`、`auto_now` 确实是隐式只读的。此外，任何在 Serializer 中定义的非模型字段（如果没写 `update`）或 `SerializerMethodField` 也是。
> 2. **取舍**：显式 (`read_only=True`) 放在字段声明旁最清晰；`Meta.read_only_fields` 适合批量定义。

### Q2. [Django/ORM] get_or_create 的执行逻辑与返回值
简述 Django ORM 中 `get_or_create` 的执行逻辑（在数据库层面是怎样查询和插入的），它的返回值是什么结构？

**答案**: `get_or_create`首先会执行 `SELECT * FROM LIMIT 2`，如果发现没有匹配的数据，就会执行 `INSERT`语句创建数据。返回的结构是“匹配到的/创建的 Model 实例+一个布尔值来表示是否执行了 `CREATE` 语句”。

> 💡 **解析**：完全正确。`get_or_create` 会先尝试 `get`，失败后再 `create`。返回 `(instance, created)` 元组。

### Q3. [HTTP] 409 Conflict 状态码适用场景
HTTP 409 Conflict 状态码在 RESTful API 设计中，通常适合用来表示什么样的错误场景？请举个例子。

**答案**: 表示资源冲突。比如 `Drama` Model 中 `name` 是一个唯一键。如果试图创建“Friends”这笔数据给 B 用户，而数据库发现 A 用户已经有 “Friends”这笔数据，就会返回409 资源冲突报错。

> 💡 **解析**：非常棒。409 常用于唯一约束冲突，或者资源版本冲突（Optimistic Locking）。

### Q4. [DRF/Request] request.data 的不可变性与深克隆 (.copy() 的优雅做法)
DRF 中的 `request.data` （如 `QueryDict`）在正常情况下也是受保护不可变的。如果想要覆盖或修改传入的数据并传递给 Serializer，使用 `.copy()` 取出并修改是一种有效做法，它会有什么注意事项或者替代方案？

**答案**: 我问了 LLM，它说现代前后端分离框架中，前端传 JSON 是主流，DRF 解析 JSON 返回的就是普通的 Python 字典，天生是可变的。并不存在您说的“在正常情况下也是受保护不可变的”。如果要替代方案，如果是替代 `.copy()`，那可以用字典推导式。

> 💡 **解析**：
> 1. **纠正**：你说得对，当 `request.content_type` 是 `application/json` 时，DRF 的 `JSONParser` 确实返回普通的 Python `dict`。
> 2. **场景**：但当处理文件上传（`multipart/form-data`）时，`request.data` 是一个 `QueryDict` 实例，它是多值的且默认 **不可变**。
> 3. **最佳实践**：不要试图原地修改 `request.data`。如果需要修改，`.copy()` 转为普通可变字典是标准做法。

### Q5. [DRF/Response] 201 Created 的 Location 响应头去哪了？(重写 create 容易漏传 headers=headers 的坑)
在 DRF 中重写 ViewSet 的 `create` 方法时，有时很容易忽略设置 `Location` 响应头，标准的 201 响应中为什么需要 `headers=headers` 里的 Location？这在 REST 语义中起什么作用？

**答案**: 这也是为了前后端解耦。因为前端理论上并不会知道后端的 API 涉及。如果后端可以将前端需要重定向的 API 地址存入 `headers`，就实现了这种解耦和分工，保证前端拿到的重定向地址绝对正确。

> 💡 **解析**：准确。在 REST 规范中，201 响应应当在 `Location` 头中返回新创建资源的 URI，这样客户端无需重新组装 URL 就能知道去哪获取该资源。

### Q6. [Django/ORM] 外键查询：`filter(fk_id=1)` vs `filter(fk__id=1)` 的底层区别与 Django 智能优化
对外键进行过滤时，`fk_id=1` 和 `fk__id=1` 会产生不同的 SQL 吗？Django 在底层会做怎样的分析优化？

**答案**: 不会产生不同的 SQL。因为当设置外键时，SQL 表格中就会建立一个 `fk_id`的字段，来保存外键的 Primary Key 的值。即便过滤时使用 `fk__id=1`，ORM 也会很聪明地去查询 `fk_id`这个字段。

> 💡 **解析**：是的。`fk_id` 是直接访问数据库字段，效率最高且不涉及额外 Join。Django 对 `fk__id` 也会直接映射到 `fk_id` 而不会真的去做对 ID 表的 Join。

### Q7. [Django/DRF] ViewSet 隐式分页陷阱 (pagination_class = None)
在 DRF 的 ViewSet 中，如果全局开启了分页，通过局部设置 `pagination_class = None` 可以关闭分页。此时框架返回的数据结构（比如有无 `results` 或 `count` 键）会发生什么根本性变化？前端如果没有容错会发生什么？

**答案**: 此时框架返回的数据结构就没有`results`或 `count`之类的键了。前端如果没有容错，就直接报错了。因为数据结构都变了。

> 💡 **解析**：是的。分页时返回的是 `{"count":..., "results": [...]}`，不分页则直接返回 `[...]`。这是导致前端 `data.results.map` 崩溃的经典原因。

### Q8. [Tiptap/Vue] 节点属性扩展 (`addAttributes` 中的 parseHTML 与 renderHTML)
在 Tiptap 中给节点扩展自定义属性时，`addAttributes` 里的 `parseHTML` 和 `renderHTML` 分别起什么作用？

**答案**: `parseHTML`是将 DOM Tree 中的属性等解析成一个 JSON 数据结构。而 `renderHTML`则是将这样一个 JSON 数据结构再换成成一个包含有效属性的额 DOM Tree。

> 💡 **解析**：正确。这是 Tiptap 双向绑定的核心：从 HTML 到编辑器内部状态（Parse），再从状态回流到预览/导出 HTML（Render）。

### 1. API-First 契约设计的深层优势
不仅仅是“并行开发”。它为自动化提供了基础：
- **生成文档**：Swagger/Scalar UI 随契约自动更新。
- **类型安全**：前端可以用 `openapi-typescript` 直接生成完整的 TypeScript 接口定义。
- **自动测试**：后端可以针对契约进行契约合规性测试。

### 2. 多模态原生语音生成的选型 (Native Audio Output)
在 Lingua Workbench 的 English Corner 中，我们正考虑放弃传统的 `OpenAI TTS` 转而拥抱 `Gemini 2.5 Flash` 的原生音频输出（若可用）或流式方案：
