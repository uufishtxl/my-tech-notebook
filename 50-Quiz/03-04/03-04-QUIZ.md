### Q1. [x] [Django/DRF] `read_only_fields` 的防御边界
在定义 `Serializer` 时我们设置了 `read_only_fields = ['status']`。
请问：
1. 如果前端发送 `{"title": "New", "status": "published"}` 的 POST 请求，`status` 字段会被验证并采纳吗？
2. 如果你在后端的 `perform_create` 或者 `Model.objects.create()` 里强行传入 `status="published"`，这个字段能被存入数据库吗？为什么？

**答案**: 1. 不会被采纳；2. 在后端这么做会存入数据库。因为 Serializer 的 `read_only_fields` 只是防止客户端写入特定字段，位于服务端的此类逻辑不会被拦截。
> 💡 **解析**：完全正确！`read_only_fields` 只是 DRF API 序列化层的一个“防弹衣”，前端传的无论什么恶意字段只要在名单里就会被直接丢弃。但是它完全防不住你在后端直接操作 ORM (`save()`, `create()`)，这也给了我们用 `perform_create` 塞入服务器私货的极佳灵活性。

### Q2. [x] [Django/DRF] ViewSet 多把枪（多种序列化器）的智慧调度
在使用 `ModelViewSet` 时，默认我们只用一把枪：`serializer_class = ArticleListSerializer`。
如果我想实现“列表返回阉割版数据（使用 `ArticleListSerializer`），而创建文章时返回带所有关联对象的豪华版数据（使用 `ArticleCreateSerializer`）”，我该如何优雅地重写某个方法来实现因地制宜？

**答案**: 应该重写 `get_serializer_class(self)`来进行因地制宜。顺便，可以通过 `self.action` 获取到 HTTP 提交的 HTTP methods，来进行具体的判断。
> 💡 **解析**：正确！重写 `get_serializer_class(self)` 是核心。通过 `if self.action == 'list':` 返回列表序列化器，`elif self.action == 'create':` 返回创建/详情序列化器。这是 DRF 视图魔法中最常用的一招。

### Q3. [x] [Django/Models] JSONField 的终极容错：`default=dict` 的防御艺术
对比 `ai_response = models.JSONField(null=True)` 和 `ai_response = models.JSONField(default=dict)`。
为什么在现代数据密集型应用中，强烈推荐使用后者？它能从物理代码层面为你减少什么恶心的判断逻辑？

**答案**: 因为前者的话，需要前后端都要进行大量的双重验证（是否为空/是否为空字典）。而使用后者，Serializer 会去保证写入这个字段的值不会是 `None`。
> 💡 **解析**：正确且直击痛点。`default=dict` 的伟大在于**防御性编程**，能帮你在所有做业务逻辑（如 `data.get('key')` 或 `for k, v in data.items()`）时避免直接抛出 `AttributeError: 'NoneType' object has no attribute 'get'`。你不再需要写恶心的 `if ai_response is not None:` 判断。

### Q4. [ ] [Django/DRF] `serializer.data` 与底层 Model 实例的鸿沟
假设前端传来的数据只有 `title`，反序列化 `serializer.save()` 成功后，你打印 `serializer.data` 发现里面没有 `content` 的默认值，但数据库里面其实有。
为什么 `serializer.data` 会和真实的 Model DB 存入的数据存在这种“失真”或截断？受什么核心契约的限制？

**答案**: 会这样吗？这我还真没试过。过。
> 💡 **解析**：这是一个经典的 DRF 坑！`serializer.data` 输出的内容，**永远严格受限于 `Meta.fields` 里面定义的白名单契约**。就算你用 `Model.objects.create()` 保存了一个自带非常多 `default="xx"` 或者自动生成的字段（比如时间戳）的实例，如果这个字段没有写进你的 Serializer `fields` 列表里，`serializer.data` 绝不会把它吐出来给前端！它是一份严格按图纸施工的输出。

### Q5. [x] [Vue/DOM] `getBoundingClientRect()` 与视口定位
请解释什么是 `element.getBoundingClientRect()`？如果我们要实现一个“元素滚动到屏幕中间时就高亮”的功能，通常会利用它的哪个返回值配合 `window.innerHeight` 来计算？

**答案**: 会返回`element.getBoundingClientRect().top`来配置计算。也就是元素距离视口顶端的距离。
> 💡 **解析**：正确！`top` 这个值表示元素顶部距离当前浏览器**视口 (Viewport)** 顶部的像素距离。配合 `window.innerHeight / 2` 就可以算出元素是不是刚好进入了屏幕的中间位置（用于做阅读器的 Scroll Spy）。

### Q6. [x] [Vue/Tiptap] 节点属性扩展与 `parseHTML` / `renderHTML`
当我们在 Tiptap（或 ProseMirror）中定制一个富文本扩展插件，并且需要为节点新增自定义属性（比如 `highlightColor`）时，`parseHTML` 和 `renderHTML` 各自的职责是什么？

**答案**: `parseHTML`负责将 `DOM Tree`解析为一个 JSON 数据；`renderHTML`则负责将 JSON 数据还原成一个 `DOM Tree`。
> 💡 **解析**：思路方向对了一半，但不够精确。
> - `parseHTML` 的职责更像是“提取规则”：当编辑器碰到一段现有的外部 HTML `<span color="red">` 时，它要告诉编辑器怎么把 `red` 抓取出来，存进 Tiptap 内部引擎内存里的 JSON 属性树中。
> - `renderHTML` 是“宣发规则”：当编辑器内部 JSON 有一个属性 `{ color: "red" }` 时，它负责把这个内存数据吐回成真实的 DOM 标签 `<span class="text-red">` 渲染到屏幕上。

### Q7. [x] [Python/Dataclasses] `frozen=True` 的化学反应
在定义 `@dataclass(frozen=True)` 时，除了让这个类的实例变为“不可变（一旦创建不可修改）”之外，它还能在底层激活 Python 的哪一个关键特性，使得这个实例可以作为字典（dict）的 Key 或放入集合（set）中？

**答案**: 能激活 Python 的 `__hash__`关键属性，实例可哈希，也就可以作为 `dict` 的 `key` 值，并且放入集合中可以自动去重。
> 💡 **解析**：完美！在 Python 中，只有**不可变对象 (Immutable)** 是可以被哈希计算（Hashable）的（比如 tuple, string）。加上 `frozen=True` 后，内置库会为你自动生成 `__hash__()` 方法。

### Q8. [x] [Vue] 危险的 `:key index` 渲染风险
为什么在 Vue 的 `v-for` 中，使用 `v-for="(item, index) in list" :key="index"` 是一件极度危险的事情（特别是列表中有 input 输入框或者拖拽排序逻辑时）？这会导致底层发生什么经典的“就地复用”错乱？

**答案**: 因为 Vue 对 `v-for` 的渲染机制是就地渲染。如果通过这样的方式绑定 `index`，列表中有插值或发送顺序变化时，会造成渲染顺序和列表顺序不一致的情况。
> 💡 **解析**：非常到位！这就是著名的**就地复用 (In-place patch)** 问题。如果你删除了第 1 项，原本的第 2 项就会变成 index 1。Vue 拿着新旧虚拟 DOM 对比，发现 index=1 还在呀！它就不会销毁并重建那个 DOM，而是直接沿用旧 DOM。结果就是，原来这个位置上的输入框内容、拖拽状态，会像幽灵一样“继承”给下一个元素。所以必须用独一无二的 `item.id` 作为 `:key`。

### Q9. [x] [Python/Requests] `raise_for_status()` (Fail Fast)
我们在写 `requests.get()` 调用外部 API 时，为什么强烈建议追加一行 `response.raise_for_status()`？如果漏掉这一行，遇到 `404 Not Found` 或者 `500 Server Error`，后续的 `response.json()` 代码会遭遇什么问题？

**答案**: 我已经对这题目模糊了，是不是和 `get_object_or_404()` 的功能类似？可以让全局的 DRF 框架对问题进行处理。遇到 `404 Not Found`和 `500 Server Error` 都可以让后续的 `response.json()`甄别和处理错误和正常的回复。
> 💡 **解析**：不太对哦。`raise_for_status()` 是 `requests` 库自己的一个方法，它的作用是 **Fail Fast (快速失败)**。
> 如果你不用它，`requests` 即便收到 `500 Server Error` 或者 `404 Not Found` 也**不会报错**！它会默默地存一个不包含正常数据的 response。然后代码继续往下走，当你执行 `response.json()` 试图解析一个 404 返回的 HTML 错误页面时，程序会直接爆出一个极其恶心难懂的 `JSONDecodeError`。加了这一行，它就会在遇到非 200 状态码时，直接原地抛出清晰的 `HTTPError: 404 Not Found`，极佳地保护了代码。

为什么传统的“内网穿透”中在个人路由器直接开放端口 (Port Forwarding) 极度危险？

- **隐形网段**：网络层面，它并不会帮你去映射外网门牌号，而是建立起一个专有的虚拟局域子网（VPC 常位于 `100.x.x.x` 幽灵网段）。
- **上帝视角**：你在外拿出手机，打开 Tailscale 的开关，立刻获得了接入这张私人虚拟图纸的门票，可以完全像连着自家的 5G Wi-Fi 一样，使用 `100.x.x.x:8000/api` 愉悦且绝密地调戏你的后端代码。
