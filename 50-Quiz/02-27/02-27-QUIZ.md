### Q1. [Database] 事务隔离级别 (RU->RC->RR->S) 
简述从 Read Uncommitted 到 Serializable 的四个事务隔离级别，并说明它们各自解决的并发问题（如脏读、不可重复读、幻读）。

**答案**: 从低到高排列如下：
- RU (Read Uncommitted): 是最脏的数据。会读到别人还没有存盘（Commit）的脏数据
- RC (Read Committed)：次之。事务的每一行查询开始时，都会储存新的快照。因此，如果别人中途提交了，第二行 SQL 查询时的数据可能变了，不可重复读。这是 Django / PostgresSQL 默认的行为。
- RR (Repeatable Read)：只在事务开始的第一行 SQL 保存快照。然后全程复用。因此哪怕别人提交了新的更改，当前事务的快照里仍然是可重复读的。这是 MySQL 的默认行为。
- S (Serializble)：放弃快照，全部加锁。会将数据直接锁死，禁止并发。

如果要修改事务隔离级别，比如在 Django 项目中，可以在 `settings.py`中进行配置。

> 💡 **解析**：✅ 完全正确！这四个隔离级别分别解决了不同的并发读写问题。值得一提的是，RR 级别下依然可能有特定条件下的幻读现象（但在 MySQL 的 InnoDB 中通过 MVCC 很大程度避免了幻读）。

### Q10. [New: Huey/Background] @task() vs @db_task() (后台任务防 MySQL 炸连接池必加 db_task)

## 🌟 今日新知 (New Knowledge)

### 1. [New: Django/Architecture] Django App 的边界拆分 (standalone apps)
在设计 Django 工程时，遵循 Standalone Apps 原则拆分各模块的好处：
1. **解耦业务逻辑与表结构**：防止各种互不相关表的 models 堆积如山造成灾难性耦合。
2. **可移植可复用**：各个 app 例如阅读器 Reader, 番茄钟 Pomodoro 将能直接当做轮子植入其他工程使用。
3. **隔离路由与模板结构**：便于管理应用级别的独立 URL 路由、测试用例等。

### 2. [New: Frontend/State] 有限状态机 (FSM) 降低 Vue/Pinia 复杂度
利用单一枚举状态代替离散多条布尔状态：
1. **杜绝不可能状态组合发生**：单变量在语言层面根本杜绝了出现 "既A也B" 这种矛盾的冲突问题。
2. **业务流程更清晰**：状态转换（Transition）仅需更新此一变量。
3. **渲染模板极大简化代码**：不再需要大量复杂的&&，||逻辑表达式即可控制组件显示隐藏。

### 3. [修正: Python/Dictionary] `hasattr` 作用于字典的隐藏陷阱
检测字典是否包含某一个键时**必须使用 `in`**（例如 `if 'color' in somedict:`）。千万**不要使用** `hasattr(somedict, 'color')`！
这是因为 `hasattr` 是用于检测对象（Class）属性的内置方法，当它作用于普通的 Dictionary 字典对象时，**它内部本身并不会抛出任何形式的 Error 报错**，而是会默默地返回 `False`（因为字典确实没有这个自身属性）。这会让程序表面上成功运行执行过去，但实际上内部逻辑全乱，进而导致产生极难追踪排查的逻辑 Bug（Silent Failure）。

### 4. [RESTful 设计] `Location` 头部字段的“正统”作用
在成功创建资源（`201 Created`）后，后端通过 `get_success_headers` 在 Response Headers 中返回 `Location` 字段。
- **作用**：提供新资源的 **API 端点 URL**（例如 `/api/v1/articles/42/`），而非原始网页 URL。
- **痛点解决**：实现 **HATEOAS** (资源发现) 与 **前后端解耦**。前端无需手动拼接 URL（`/api/articles/` + `id`），而是直接读取 `Location` 头部进行后续跳转或请求。虽然在返回完整 JSON Body 的简单场景中可被忽略，但在高标准的工业级架构和第三方集成（如自动化测试、Zapier 等）中是必备的协议契约。

### 5. [DRF/ViewSet] `get_object()` 的运作内幕与 404 容错
在 ViewSet 的 Member Action 中调用 `self.get_object()`：
- **本质**：它不是将数据转为字典，而是根据 URL 中的 `pk` 去 `get_queryset()` 中提取出那条 **Python 模型实例对象**。
- **优势**：它能自动打理 **404 响应**。如果 ID 不存在，它会直接抛出 `NotFound` 异常并返回标准的 HTTP 404 JSON，让代码逻辑异常整洁。

### 6. [Django/ORM] `JSONField` 的赋值魔法与“原地修改”陷阱
Django 中的 `JSONField` 让存储字典/列表变得像操作普通变量一样简单：
- **自动转换**：赋值时直接给字典 `obj.json_field = {'a': 1}`，Django 会在 `save()` 时自动调用 `json.dumps()`；读取时自动 `json.loads()` 还原为字典。
- **致命陷阱（In-place Mutation）**：如果你直接修改字典内部的值（如 `obj.json_field['key'] = 'new'`)，Django 的变更追踪机制**无法感应到**子项的变化，导致 `save()` 后数据库不会更新。
- **最佳实践**：必须**重新赋值整个对象**（如 `data = obj.json_field.copy(); ...; obj.json_field = data`）来确保触发数据库更新。
