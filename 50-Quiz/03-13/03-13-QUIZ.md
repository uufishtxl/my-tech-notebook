### Q4. [Requests] raise_for_status() 的 Fail Fast 原则
在 Python 中调用第三方 API（如 Google Translate 或 Gemini）时，使用 `response.raise_for_status()` 的作用是什么？如果不加这一行，当 API 返回 500 错误时，后续代码可能会遇到什么隐患？

**答案**: 如果第三方 API 返回的是一个 Error Response，通过 `raise_for_status()`就可以正确捕捉到这个错误，并且通过全局的 DRF 的错误处理机制来返回错误给请求端。如果没有这么做，不会将第三方 API 返回的错误作为“错误”来处理，而是会作为正常的 Response 返回给客户端，客户端读取 Response 事，就会瘫痪。

> 💡 **解析**：**非常精准**。如果不加，代码会继续尝试解析一个可能是“错误详情”的 JSON 作为“业务结果”，导致程序在离错误发生地很远的地方崩溃，增加调试难度。这就是 **Fail Fast** 的核心。

### Q6. [Vite/DevOps] Proxy & Localhost
在前端 `vite.config.ts` 中配置 `server.proxy` 的核心目的是什么？在开发环境下，它是如何帮助我们绕过浏览器的同源策略（CORS）限制的？

**答案**: 核心目的就是可以避免浏览器的严格检查并且进行拦截，也就是所谓的 CORS Policy。它其实是在 Node 环境下开启了一个后端微服务。这样后端与后端之间的通信就不会受到浏览器的影响。这个微服务会负责转发，微服务本身和前端享有同一个端口，因此同样也不会受到浏览器的拦截。

> 💡 **解析**：**完全正确**。Vite Proxy 是开发环境下的“挡箭牌”，通过欺骗浏览器（让它以为是在请求同源路径），再由 Node 在服务器侧代劳完成跨域。

### Q7. [Huey/Background] @task() vs @db_task()
在我们的 Django 后端处理单词释义异步增强（`enrich_word_node`）时，为什么要优先使用 `@db_task()` 而不是普通的 `@task()`？在高并发任务场景下，忽略这一点可能导致数据库连接池出现什么问题？

**答案**: 因为 `@db_task`会妥善地处理数据库的连接，也就是在逻辑完成后，总是及时地关闭连接。如果使用 `@task`去连接SQL并进行操作，就有可能在高并发时，导致连接池枯竭。

> 💡 **解析**：**满分**。`@db_task` 会自动打开/关闭连接，尤其在异步 worker 中非常关键，它是维护数据库资源池的防线。

### Q9. [Architecture] N+1 问题与 select_related
在 `EnglishCorner` 的 `ConversationDetailSerializer` 中，如果我们需要同时显示每条 Message 所属的 Scenario 标题，但没有在 QuerySet 中使用 `select_related('scenario')`，会发生什么现象？请描述 N+1 问题的表现及其优化方案。

**答案**: 会发生N+1 查询的问题。所谓 N+1 就是将原来可以通过 `JOIN` ，使用 1 - 2 次 SQL 查询的数据库查询事务因为使用遍历而变成了 n+1 次 SQL 查询事务，给 SQL 带来压力。优化方案就是使用 `prefetch_related` 或者 `select_related`。

> 💡 **解析**：**正确**。总结得很好。`select_related` 用于一对一和多对一（单表 JOIN），`prefetch_related` 用于多对多和一对多（分别查询再 Python 侧合并）。

### Q10. [API] Idempotency (幂等性)
请解释 PUT 方法和 POST 方法在 RESTful 语义上的幂等性差异。如果用户在网络不稳定的情况下连续点击了两次“创建对话”按钮，为什么我们建议在架构设计上考虑幂等性？

**答案**: PUT 方法是替换整个数据行，因此是幂等的。而 `POST`则是创建新数据，这就不是幂等的。

> 💡 **解析**：**正确**。幂等性保证了“即使操作执行了多次，结果依然一致”。在网络抖动时，幂等设计能防止数据库里塞满重复的“僵尸对话”。
