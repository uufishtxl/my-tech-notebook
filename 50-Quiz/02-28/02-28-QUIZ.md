### Q1. [DRF/Validation] is_valid(raise_exception=True) 的核心机制
`is_valid(raise_exception=True)` 是如何实现 Fail Fast 的？抛出的异常是如何被 DRF 转换成标准 HTTP 400 响应的？

**答案**: 当验证失败时，会抛出 `ValidationError`，DRF 的外层框架封装了全局的异常处理器，可以捕获它并组装出自动响应 400 的错误抛出。


> 💡 **解析 (🟢 ✅ Correct)**：DRF 的 `is_valid(raise_exception=True)` 就是通过在验证失败时直接跑出 `ValidationError`，被 DRF 外层全局异常拦截器捕获后转化为 400 返回，这样你不需要在每个 view 写 `if not is_valid(): return Response(400)`。

### Q2. [DRF/Serializer] serializer.save() vs model.save()
在 DRF 中直接调用 `model.save()` 和通过 `serializer.save()` 保存数据有什么核心区别？为什么优先推荐 `serializer.save()`？

**答案**: `serializer.save()`可以让 Serializer 参与到数据的验证中，并且可以自动判断，是需要 `PUT` 还是 `POST`。


> 💡 **解析 (🟢 ✅ Correct)**：在处理复杂验证时，`serializer.save()` 可以确保验证逻辑的一致性，同时也帮助分发内部数据到 Model，隔离了前端 JSON 与后端 ORM 的裸接触。

### Q4. [Frontend/State] 有限状态机 (FSM) 降低 Vue/Pinia 复杂度
在使用 Vue 或 Pinia 管理复杂 UI（比如有倒计时、翻转、多种显示模式的组件）时，引入有限状态机 (FSM) 思想能解决什么痛点？

**答案**: 如果用多个Boolean值来控制状态，那么需要人为维护不同状态的相斥性，很有可能因为维护不当而出现问题。用状态机则可以完美解决这一困境。 


> 💡 **解析 (🟢 ✅ Correct)**：使用 FSM（利用 `mode` = 'TIMER' | 'HISTORY'）避免了大量相互冲突的 `isTimerStarted`, `isFlipped`, `showSettings` 等 boolean 值互相踩踏的问题。

### Q5. [RESTful 设计] Location 头部：进阶资源发现与标准契约
在创建资源（POST 请求成功，返回 201 Created）时，HTTP 响应中包含 `Location` 头部有什么作用？

**答案**: 这样，当前端需要在接收到POST请求的响应结果后根据结果来进行页面跳转时，就可以直接从 Header 的 `Location`中获取地址，这是最稳定的，也是一种解耦的方式。如果前端根据 `pk` 值，如果后端并不是按前端预想的方式指定的 URL，就会跳转失败。


> 💡 **解析 (🟢 ✅ Correct)**：RESTful 标准中 HTTP 201 Created 的推荐做法：后端负责分配和组装新资源的 URL 放在 `Location`，前端可以直接跳转，无需猜测 URI 结构。

### Q7. [Django/ORM] JSONField 自动化之上的“原地修改”失效陷阱
如果在 Django ORM 的 JsonField 中直接通过字典引用修改深层嵌套的值（例如 `obj.my_json["data"]["key"] = "new_value"`），然后直接调用 `obj.save()`，可能会遇到什么坑？如何确保修改生效？

**答案**: `JSONField`无法原地修改。因此题目中的修改方式会失效。正确的修改方式是取出字典，用 `copy` 复制一个字典，然后将复制的字典更新好后，将复制后的字典复制给 JSON 字段名。


> 💡 **解析 (🟢 ✅ Correct)**：注意：深浅拷贝或者对字典直接利用重新赋值更新，因为 JSONField 不追踪内嵌字典的变化，仅仅只有赋给大字段一个新的字典对象才会触发 `save()` 将其保存（因为底层序列化检查的是大对象的改变）。

### Q15. [LangGraph/Tools] Tool Node 异常处理
在 LangGraph 中设计工具 (Tool) 给 Agent 调用时，为什么原则上不要让工具直接 `raise Exception`，而是推荐将错误信息以 `Return String` 的方式返回给 Agent？

**答案**: 因为一旦 `raiseException` 就会报错，让整个程序崩溃，出现服务器内部错误。而用 `Return String`不但不会造成程序崩溃，还可以依赖 LLM 的 Reasoning 机制来进行自我纠正。


> 💡 **解析 (🟢 ✅ Correct)**：是的，直接崩溃中断了 Agent 与大模型的闭环，如果把报错的详细字符串返回给大模型，它的推理引擎就能知道哪里出错了，并且再次提供正确的参数再次尝试调用，也就是所谓的自愈 (Self-Correction)。

## 🌟 今日新知 (New Knowledge)
1. **Tool 参数重载与灵活查询 (Optional Arguments)**
   当 AI Agent 卡在必要参数不存在时，不要只改 System Prompt 让它凭空猜，而是要在底层的 Python Tool 中引入 `Optional` 参数（如 `annotation_id: Optional[int] = None`）。并在方法内编写“通过可用 ID 查表关联未知 ID”的“垫片代码”，避免抛出底层崩溃，从软硬件双管齐下治愈 AI 的调用卡顿。

2. **针对工具调用的显式路径引导 (Explicit Path Guidance)**
   有了底层工具的灵活参数不够，LLM 由于其“字面倾向性”，当参数签名变化时可能会视而不见。在 System Prompt 中加入具体的 Action Rule（例如 `如果只有注释 ID，传入 annotation_id=... 到 get_reader_context`）可以强关联“手头的数据”和“新的参数入口”，为它的推理建立“思维导图”，打通显式路径。
