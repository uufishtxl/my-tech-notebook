请按从“最宽松容易出问题”到“极其严格防并发”的顺序，列出关系型数据库事务四个隔离级别的缩写（RU, RC, RR, S）。

**答案**: RU > RC > RR > S？其实我就记得RC了，也找不到之前的笔记了。
> 💡 **解析**：`[ ]` 没关系，这个纯八股文知识点确实容易忘。你的顺序（从小到大）排对了！但需要记住全称以便应对面试或复杂的高并发场景查错：
> 1. **RU (Read Uncommitted)**: 读未提交（级别最低，极易产生脏读）。
> 2. **RC (Read Committed)**: 读已提交（PostgreSQL / SQL Server 的默认级别，防了脏读，但会产生不可重复读）。
> 3. **RR (Repeatable Read)**: 可重复读（MySQL InnoDB 默认级别，防了不可重复读，配合间隙锁极大缓解了幻读）。
> 4. **S (Serializable)**: 串行化（性能最差，但是绝对安全）。

### Q17. [Python/Dictionary] 字典与 hasattr() 的迷局
在 Python 中执行 `hasattr({"color": "blue"}, "color")` 返回的结果是 True 还是 False？如果你想判断一个东西到底在不在字典里，应该使用什么语法？

**答案**: 返回的是 `True`。没理解，不就是用这个语法就可以判断了吗？
> 💡 **解析**：
> 这是一个无数新手甚至老手都会踩进去的 Python 级核心深坑！
> 正解是：**`hasattr()` 会返回 `False`！！！**
> 
> **为什么会这样？**
> `hasattr(obj, name)` 这个函数专门用来判断一个**对象（Object，如类的实例）**有没有某个**属性或方法**。例如对于 `class User(name="Alice")`，你可以用 `hasattr(user_obj, "name")` 来得到 True。
> 
> 但是！字典（`Dict`）只是一种**容器数据结构**，里面的 `"color"` 仅仅是作为一个键（Key）存进去的数据，而不是这个字典对象自己主动长出来的**代码属性**！所以如果你用 `hasattr` 查 `"color"` 它会无情地报错返回 False。但如果你查 `hasattr(my_dict, "keys")` 它就会返回 True（因为所有的字典都有 `.keys()` 这样一个自带的方法）。
> 
> **正确的姿势**：要想判断字典里到底有没有这个关键字，永远只用最快的 `in` 语法。
> `if "color" in dict1:` (这才是 Python 唯一且最正确的字典检验方法！)

### Q18. [Python/Typing] TypedDict 为什么在图框架中被推崇
像 LangGraph 在编写 `AgentState` 这个共享大黑板时，为什么选择用 `from typing_extensions import TypedDict` 而不直接用原生的空字典类型（`dict`）？它在开发和编码体验上有什么极其显著的好处？

**答案**: 空字典类型是一种 loose typing，能够获得的信息很有限。现在的开发趋势就是用强 typing。但是可能这个回答太泛泛而谈了。
> 💡 **解析**：
> 思路对的（松散 vs 强类型）。具体到落地实战体验上，`TypedDict` 对开发者最致命的好处体现在两点：
> 
> 1. **IDE 的代码护航与智能防呆（最显著的好处）**：
> 假如只是普通的字典，你在后面准备读取变量敲出 `state["` 的时候，VSCode 会像瞎子摸象，完全不给你任何代码补全。而且即使你手滑写成了 `state["mesages"]`，编辑器也不会纠正，直到运行起来系统崩掉。
> 但用了 `TypedDict`，当你敲出 `state["` 时刻，VSCode 会“唰”地一下弹出下拉列表：`messages`, `next`, `context`, `sources` 供你直接回车选择。这就是强类型带来的震撼编码体验！
> 
> 2. **约束大型架构的读写白名单权限**：
> 在复杂的状态图里，决不允许某些游荡的 Agent 随心所欲地往大黑板里乱塞垃圾变量（比如偷偷塞个 `state['tmp_token']`）。`TypedDict` 相当于是一份法定的只准包含这 4 个字段的契约。只要有人试图读写别的键，类型检查器（如 MyPy 或 Pylance）第一时间就会在屏幕上下红波浪线严词拒绝。
